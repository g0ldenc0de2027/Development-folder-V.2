# Целевой контур локальной и общей базы знаний

Версия: 0.5.0. Дата: 2026-11-16. Автор: OpenAI Codex, GPT-6.
Статус: DRAFT / NOT READY. Это архитектурная спецификация будущего этапа, не допуск к реализации.
Связанные документы: spec/local-knowledge.md, specification-system/tz_state.md, правила 1, 17 и 20.

## 1. Цель и решения владельца

1. Одна папка разработки соответствует одному проекту; локальная БЗ принадлежит только ему.
2. Локальная БЗ сохраняет ценные знания, факты, решения, требования, ограничения, уроки,
   источники и проверенные результаты только этого проекта.
3. Общая БЗ накапливает важные знания из локальных БЗ всех проектов и прямые записи владельца
   на любую тему. Её область не ограничена разработкой, межпроектными уроками или повторным
   использованием.
4. Общая БЗ — общий источник для всех допущенных проектов и агентов. Это не означает
   безусловную выдачу каждой записи каждому агенту; область, классификация и аудитория
   ограничивают доступ.
5. В начале содержательной задачи агенты проверяют обе БЗ. Если достаточных сведений нет
   или решение тяжёлое/неясное, обязателен исследовательский цикл из правила 20.
6. Результаты работы сохраняются сначала в локальной БЗ проекта. Ценное для портфеля,
   важное для общей картины или прямо указанное владельцем предлагается в общую БЗ после
   проверки, а не копируется туда автоматически.
7. Обработка по умолчанию локальная. Передача текста, файлов, фрагментов, эмбеддингов или
   запросов внешнему поставщику разрешена только для явно одобренных данных.
8. Аналоги дают идеи и проверяемые требования; донорский код и готовые реализации не копируются.

## 2. Область и границы

Входит в целевую систему:

- локальная и портфельная память с общей схемой происхождения и версионирования;
- поиск в локальной и общей БЗ, возврат источников и точных ревизий;
- исследование пробелов, экспертные задания и проверка выводов;
- запись знаний в локальную БЗ и контролируемое продвижение в общую;
- безопасная обработка основных типов файлов с явным статусом возможностей;
- переносимое хранение, offline-режим, резервирование и восстановление;
- связь с мультиагентным контуром без смешения знаний и оперативной переписки.

Пока вне допуска: реализация федеративного поиска, ACL, publisher, parser workers,
embeddings, OCR/ASR, рой агентов, UI, новые форматы хранения и миграция схемы.
Для каждого такого объёма нужна собственная проверенная задача и READY-допуск.
Текущий срез T-004 и его приёмка остаются ограниченными файловым Markdown/JSON CLI.

## 3. Модель данных и источника истины

Физический путь не является идентификатором. У базы есть постоянный логический ID; у проекта —
постоянный project ID. Папку можно перенести на другой диск, обновив только локальную
настройку подключения. В публичных и переносимых данных не фиксируется абсолютный путь ПК.

Для каждой записи целевая схема хранит как минимум:

- постоянные IDs записи и коллекции, origin project ID при наличии, тип и язык;
- область: проектная или портфельная; классификацию и явную аудиторию;
- состояние: draft, reviewed, accepted, superseded, withdrawn или processing state;
- источник, ссылку/локальный locator, точную исходную ревизию или SHA-256 и дату получения;
- дату утверждения, актуальность, valid-from/valid-until и дату следующей проверки;
- происхождение преобразования: original hash, parser/extractor version и derived hash;
- ссылки на доказательства, применимость, известные противоречия и решение ревьюера.

Прямое сообщение владельца имеет provenance owner-provided. Оно не переименовывается
в независимо проверенный факт без источника или подтверждения. Обновлённая запись создаёт
новую ревизию; принятая старая версия становится superseded, отозванная — withdrawn.
Отзыв или устаревание исключает запись и производные фрагменты из обычной выдачи.

При конфликте действуют ограничения безопасности и прямые решения владельца; для конкретного
проекта его утверждённое ТЗ и актуальные решения имеют приоритет над общей рекомендацией.
Для изменяемого внешнего факта свежий первоисточник важнее старого пересказа. Draft,
ответ агента или результат поиска сам по себе не становится правилом или фактом.

## 4. Рабочий цикл для каждой задачи

### 4.1 Приём и предварительный поиск

1. Зафиксировать проект, задачу, ожидаемый результат, ценовые/безопасностные риски и класс данных.
2. Проверить локальную БЗ текущего проекта и подключённую общую БЗ. Если общий путь задан,
   но недоступен, вернуть это как явное состояние, не подменяя другой коллекцией.
3. Искать по требованию, компоненту, ошибке, стеку и ID. Получить записи по найденным ID.
4. Для каждого использованного вывода сохранить collection ID, record ID, status, точную
   ревизию/hash, источник и дату проверки. Draft и неподтверждённый импорт показывать как
   подсказки, а не как достоверную рекомендацию.
5. В текущем CLI это два ручных запроса: одна коллекция за вызов. Ни интеграцию, ни общий
   запрос одного агента к обеим БЗ пока не заявлять.

### 4.2 Проверка достаточности и исследование

Результаты поиска оцениваются по релевантности задаче, статусу, источнику, свежести,
совместимости и области применения. Пустая выдача не доказывает отсутствие знания:
учитываются полнота индекса, ошибки парсинга и недоступные источники.

Если применимых и актуальных сведений не хватает, проверить первичные источники и выполнить
уровень исследования R0–R3. Для тяжёлых случаев по правилу 20 обязательны OSINT, Deep Research,
профильные экспертные роли и сравнение наилучших выполнимых альтернатив. Задание эксперту
содержит точный вопрос, ревизию, read/write scope и ожидаемое доказательство. Внешним
экспертам нельзя передавать закрытый контекст без отдельного допуска. Спорные выводы и
непокрытые области отмечаются; без достаточных доказательств решение не считается проверенным.

### 4.3 Выполнение и сохранение в локальную БЗ

По завершении сохранять в локальной базе проверенные проектные решения, полезные факты,
ошибки и уроки. Каждая запись должна иметь источник и привязку к требованию, задаче,
коммиту, версии или наблюдению, когда они существуют. Отделять факт от предположения,
решения, рекомендации и цитируемого мнения. Полные транскрипты и изменчивый runtime агента
не принимать как долговечное знание автоматически.

### 4.4 Предложение в общую БЗ

Создать promotion proposal для знания, если оно полезно другим проектам, важно для
портфельной картины или прямо указано владельцем. Не удалять и не перемещать локальный
источник. Proposal содержит исходную запись и ревизию, краткое обобщение, причину передачи,
область и audience, классификацию, источники, redactions/transformations, срок актуальности
и проверку дубликатов/противоречий.

Проверка перед admission: provenance и права на материал; секреты и персональные данные;
scope/audience; точность и независимые evidence; freshness; дубли и противоречия;
безопасность prompt injection; пригодность для Git/backup и внешнего хранения.
Результат: accepted, returned-for-changes, rejected или restricted. Владелец может задавать
политику автоматического приёма только для явно определённых низкорисковых классов.
Изначально promotion и admission раздельны и требуют проверяемого review.

### 4.5 Использование общей записи другим проектом

Общий поиск возвращает только разрешённые записи. Для проектных записей применяются
namespace и ACL до поиска, выдачи совпадения, фрагмента, reranking, context, cache и logging.
Проект может хранить ссылку/pin на точную общую ревизию и собственную заметку о применимости.
Обновление или отзыв общей версии помечает pin устаревшим; локальное ТЗ автоматически не
перезаписывается.

## 5. Роли и граница мультиагентной системы

- Владелец задаёт цель, допустимую автономность, политику данных и принимает материальные решения.
- Главный ИИ ведёт один поток: распределяет задачи, ограничивает write-set, оценивает evidence,
  принимает локальные записи и координирует promotion.
- Профильный эксперт исследует узкий вопрос и возвращает рекомендацию, риск и недостающую
  проверку; без отдельной выдачи полномочий он не меняет чужие файлы.
- Агент-потребитель запрашивает контекст через контролируемый интерфейс, цитирует источник
  и не трактует retrieved content как system/developer instruction.
- KB broker/search router применяет идентичность, ACL, scope, freshness и лимиты до выдачи.
- Индексатор обрабатывает оригиналы в карантине с версионированными адаптерами.

База знаний не является доской задач или bus сообщений. Назначения, lease/heartbeat, блокировки
файлов, активные сообщения, состояния запусков и аудит инструментов хранятся в отдельном
контуре координации. В долговечную БЗ попадают только отобранные результаты, а не весь поток
агентских разговоров. Имена agent/author из JSON не являются доказанной аутентификацией;
до появления brokered identity нельзя обещать надёжную изоляцию агентов одного процесса/учётной
записи.

## 6. Доступ, приватность и внешняя обработка

Целевые классы данных: portfolio-general, internal, project-confidential, restricted.
Для каждого класса задаются допустимые роли и destinations. Неизвестная классификация или
отсутствующая identity означает fail-closed для ограниченной записи. Общая БЗ может содержать
проектную запись, но она не становится доступной всем проектам от факта копирования.

GitHub, облачная синхронизация, embeddings API, OCR/ASR provider и внешняя LLM — внешние
передачи. До egress применяется allowlist полей, redaction, минимизация контекста, назначение
и audit receipt. По умолчанию текст, медиа и эмбеддинги обрабатываются локально. Запрет или
неизвестный статус egress не обходится fallback-ом на внешний сервис.

Содержимое документов, веб-страниц, OCR и результатов агентов считается недоверенными данными.
Инструкции внутри источника не исполняются. Рискованный файл нельзя запускать для «извлечения».
Нет ACL — нет межпроектной выдачи restricted/project-confidential данных; локальный filesystem
path не заменяет механизм авторизации.

## 7. Основные форматы и статусы обработки

Единая версионируемая capability matrix должна отдельно показывать для формата: обнаружение,
безопасное хранение оригинала, извлечение, индексирование, preview, ограничения размера,
версии адаптера, локальность/egress и статус проверки.

| Группа | Целевое содержимое | Правило состояния |
|---|---|---|
| Текст, исходники и структурированные данные | MD, TXT, CSV, JSON, YAML, XML, HTML, исходный код и конфиги | Хранить оригинал; извлекать разрешённые текстовые поля без исполнения кода |
| Документы и почта | PDF, DOCX/XLSX/PPTX, ODT/ODS/ODP, RTF, EML/MSG, календарные экспорты | Отдельный адаптер для каждого формата и тестовый корпус |
| Изображения и сканы | PNG, JPEG, TIFF, сканы PDF | OCR локально по умолчанию; слой и координаты связывать с оригиналом |
| Аудио и видео | WAV/MP3/M4A, MP4/MOV и распространённые контейнеры | ASR/метаданные локально по умолчанию; внешняя обработка только с допуском |
| Архивы и составные пакеты | ZIP, TAR и другие явно проверенные форматы | Карантин; лимит размера, вложенности, времени и суммарной распаковки |
| Специализированные/неизвестные файлы | Базы, CAD, исполняемые и proprietary форматы | Безопасно хранить как opaque только если класс разрешён; не заявлять полнотекстовую обработку |

| Аудио | .wav, .mp3, .m4a, .aac, .flac, .ogg, .opus | Оригинал + технические метаданные; ASR локально по умолчанию с таймкодами и confidence. |
| Видео | .mp4, .mov, .mkv, .webm, .avi | Оригинал + метаданные; транскрипт аудио локально. Извлечение кадров — отдельная операция с лимитом и таймкодами. |
| Архивы | .zip, .tar, .gz, .tgz, .tar.gz, .tar.xz, .7z; .rar — кандидат только после проверки адаптера | Карантин; до реализации лимиты числа entries, nesting, expanded bytes, compression ratio и времени. Запрещены path traversal, symlink/reparse escape, TOCTOU и запуск содержимого. Зашифрованные архивы остаются quarantined/stored-only; никаких переборов паролей. Будущий ручной локальный разбор потребует отдельного допуска: passphrase только в памяти, без логов/сохранения/egress, производные plaintext-файлы — временные и удаляются по завершении. |
| Базы и резервные копии данных | .sqlite, .sqlite3, .db, vendor-specific dumps | Оригинал и hash; БД — stored-only до отдельной read-only sandbox/проверки. Текстовый .sql проходит правила для кода и не исполняется. |
| Неизвестное/двоичное | любое другое расширение | Только безопасное opaque-хранение при разрешённой классификации; extraction/indexing явно unsupported, без silent fallback. |

Для каждого расширения capability matrix задаёт независимо: обнаружение, оригинал,
метаданные, извлечение, полнотекстовый индекс, preview, локальность/egress, лимиты,
адаптер и проверенную версию. Зашифрованные документы, макросы, вложения, повреждённые
файлы и превышение лимита должны получать отдельный наблюдаемый статус, а не пустую
выдачу, похожую на успешную обработку.
Статусы возможностей обработки (stored-only, extracted, indexed, unsupported, stale, failed)
не заменяют отдельный статус доверия и допуска. Для каждого оригинала и каждого производного
объекта ведутся provenance, hash и отдельные processing/trust states. «Stored» не означает
«прочитан»; «extracted» не означает «проверен»; «released» означает только ограниченный
допуск к указанным операциям, а не истинность или безопасность содержимого. Исходники и
производные связаны хэшами, версией адаптера и указателями на страницы/ячейки/таймкоды.
Поддержка каждого формата вводится отдельно после security review и тестов на повреждённых
и вредоносных образцах.

### Изоляция парсеров и карантин

Любой оригинал и извлечённое содержимое — недоверенные данные. Имя, расширение и MIME
не доказывают формат или безопасность. На intake доступны только hash, размер и безопасные
метаданные; оригинал получает trust state quarantined-original. Обычные потребители, поиск,
retrieval и агентский контекст не видят карантинный объект и не получают даже его snippet,
счётчик или чувствительный идентификатор.

Предлагаемый переход состояний отделяет возможность безопасно разобрать байты от
доверия к результату:

1. quarantined-original: неизменяемый оригинал, точный hash, классификация и provenance;
   автоматический preview или разбор запрещён.
2. isolated-processing: только явно разрешённая операция с конкретным hash и проверенной
   версией адаптера выполняется отдельным процессом с минимальными правами. Это не снимает
   карантин и не открывает доступ обычным потребителям.
3. derived-quarantined: частичный или завершённый результат имеет собственный hash и связь
   с оригиналом, но остаётся недоступен через обычные preview/search/index/context/cache/
   embedding/log/egress интерфейсы.
4. review-pending: аутентифицированный reviewer получает только bounded review-only доступ
   к hash-связанному результату через отдельную инертную поверхность без исполнения
   HTML/активного содержимого, постоянного cache/index и egress. Данные остаются недоверенными;
   инструкции из источника не становятся командами.
5. authenticated decision: только проверенный receipt переводит конкретный производный
   объект в released-local с перечисленными локальными capabilities, audience и сроком
   действия либо в rejected. Допуск оригинала и производного объекта не подразумевается.
6. parser error, timeout, cancel, limit breach, hash/path mismatch, неуспешная или истёкшая
   проверка оставляют исходник quarantined; производный результат становится
   failed-quarantined/revoked, частичные файлы удаляются, безопасные метаданные ошибки
   сохраняются без содержимого.

Receipt связывает hash оригинала и производного объекта, формат, адаптер/version/config,
версию профиля проверок, классификацию и audience, локально разрешённые capabilities,
authenticated reviewer, время, срок и отзыв. Изменение любого hash, версии адаптера,
профиля/политики или классификации инвалидирует receipt и закрывает доступ до повторной
проверки. Публикация наружу никогда не следует из released-local: для каждого назначения
и набора полей требуется отдельное явное разрешение egress.

Контракт parser job: отдельный процесс/контейнер с минимальными правами; неизменяемый
read-only input для одного hash; отдельный временный каталог; запрет сети по умолчанию;
отсутствие пользовательских credentials, секретов и доступа к домашним каталогам; лимиты
CPU, памяти, времени, размера вывода, числа объектов и распаковки; отмена и очистка при
сбое. Запись разрешена только в выделенную область результата. Запрещено следовать
symlink/reparse points или подменённым путям; идентичность пути и hash повторно проверяется
перед открытием и фиксацией результата. Extracted text/OCR/ASR наследует классификацию и
audience оригинала. Технология изоляции и аутентификация ролей пока не выбраны.

Зашифрованные архивы остаются quarantined/stored-only; перебор паролей запрещён. Будущая
ручная локальная операция требует отдельного допуска: passphrase существует только в памяти,
не попадает в логи/хранилище/egress, plaintext создаётся только в ограниченном scratch,
удаляется при любом исходе, а производные результаты проходят тот же карантинный review.

## 8. Надёжность, переносимость и поиск

- Логический KB ID отделён от пути. Произвольный локальный диск/каталог задаётся через
  локальную конфигурацию; заданный, но недоступный путь даёт timeout/unavailable, не fallback.
- Каждая операция ограничена временем, объёмом, числом файлов и отменой; ошибки видимы.
  Частичная генерация не становится текущей. Повтор запроса идемпотентен.
- Канон, оригиналы и производные индексы разделены. Индекс восстановим из канона и хранит
  source generation, schema/parser/tokenizer version. Устаревший индекс не выдаёт удалённые
  или заменённые записи.
- Для будущего SQLite/другого индексного файла выбрать расположение и режим блокировок с учётом
  переносных дисков, сетевых папок и синхронизации. Не держать активную WAL-базу в файловом
  облачном sync без подтверждённой поддержки конкуренции.
- Backup и restore включают необходимые оригиналы, каталог, локальные предложения и policy,
  но секреты не попадают в общий Git по умолчанию. Восстановление сначала проверяет manifest,
  hashes и совместимость, затем атомарно активирует новую генерацию с rollback.
- Нет общего SLO latency и объёмов до baseline на целевой машине. Сначала измерить корпуса,
  диски и типы запросов; пороги утверждать по результатам.

### 8.1 Конкурентная запись, конфликты и восстановление

Предлагаемый инвариант: принятая запись не теряется из-за последнего записавшего
процесса. У каждой мутации есть operation ID для идемпотентного повтора и ожидаемая
source revision/generation. Публикация проверяет базовую ревизию сравнением-and-swap;
устаревшая база создаёт явный конфликт на повторное review, без last-write-wins.
Прямые записи нескольких агентов в один канон запрещены. Предпочтительная модель —
один локальный broker/writer на БЗ, а параллельные агенты отправляют изолированные
draft/proposal. Переносимость offline proposals не означает автоматического слияния.

Это проектное предложение, не выбранная реализация. До READY решить число процессов и
устройств, где допускаются одновременно активные writers, применение CAS на локальных,
UNC/network и sync-managed хранилищах, модель lease/lock и recovery после обрыва питания.
Атомарность одного NTFS-каталога нельзя переносить на другие файловые системы без теста.

Обязательные будущие acceptance tests:
1. Параллельные уникальные capture не теряют друг друга; повтор одного operation ID
   возвращает тот же receipt и не создаёт дубликат.
2. Два promotion от одной base revision не могут молча перезаписать друг друга: устаревший
   получает conflict и требует rebase/re-review на текущей версии.
3. Остановка процесса на каждом шаге commit не показывает частичный пакет и после restart
   сохраняет предыдущую принятую либо полностью проверенную новую generation.
4. Конкурирующий или истёкший lease не позволяет старому агенту записать поверх более
   нового владельца; конфликт виден оператору и сохраняет обе исходные proposals.
5. Те же проверки запускаются на каждой заявленной категории storage/filesystem; непроверенная
   категория остаётся unsupported для concurrent writers.

## 9. Критерии проверки будущих реализаций

1. На каждой задаче есть receipt поиска по обеим БЗ либо явный статус unavailable/incompatible;
   в receipt только доступные записи и их точные ревизии.
2. Пустая выдача при stale/failed/unsupported источнике не отображается как «знаний нет».
3. Для R2/R3 тестируется запуск исследовательского маршрута и specialist assignment; итог
   сравнивает варианты и показывает доказательства, разногласия и непокрытые зоны.
4. Для любой выданной рекомендации агент указывает применимые записи и первичные источники.
5. Promotion не меняет local original; повтор proposal идемпотентен; duplicate/conflict,
   secret/PII, неподтверждённое право и запрещённый audience блокируются.
6. Запрещённый агент не получает текст, ID, snippet, count, cache или лог restricted записи.
7. Parser tests проверяют отдельный низкопривилегированный процесс, отсутствие network/secret access, read-only input, quotas, timeout, cancel, очистку scratch и проверку output.
   Archive tests включают zip slip, symlink/reparse escape и TOCTOU гонку; OCR/ASR egress по умолчанию запрещён.
8. Отключённый диск, смена буквы диска и перенос root не вызывают silent fallback или потерю
   подтверждённых записей.
9. Backup повреждённого архива не заменяет рабочую базу; restore drill документирован.
10. Качество retrieval измеряется на эталонных запросах по языкам и форматам; изменения
    модели, parser или tokenizer помечают соответствующий derived index stale.

11. PDF fixture с JavaScript, OpenAction/AA, Launch, submit-form, remote link и embedded file не исполняется и не создаёт сетевых запросов; embedded file остаётся quarantined.
12. Зашифрованные ZIP/7z/RAR остаются в карантине; пароль не перебирается, не логируется, не сохраняется и не отправляется наружу. Разрешённая ручная операция проверяет ephemeral password и очистку plaintext.
13. Обычные consumer/API пути не раскрывают quarantined-original и derived-quarantined, включая ID, snippet и count; только явно назначенный isolated-processing может читать точный read-only hash-input, не меняя trust state.
14. Review-only доступ требует аутентифицированной роли, ограничен одним derived hash, не выполняет активное содержимое и не создаёт постоянный cache/index/log content или egress; receipt связывает source hash, output hash, parser/config и policy/check version.
15. До authenticated release обычные preview/search/index/context/cache/embedding/log/egress отклоняются; released-local предоставляет только capabilities/audience/expiry из receipt. Внешняя передача отдельно запрещена без destination-specific approval; revoke/expiry прекращает выдачу.
16. Crash, timeout, cancel, limit breach и подмена hash/path между parse и receipt не публикуют partial output, очищают scratch, сохраняют original в карантине и не создают успешный receipt.
17. Для encrypted archives password не перебирается и не логируется/сохраняется/передаётся наружу; разрешённая ручная обработка проверяет удаление plaintext на успехе и каждом отказе.
18. Если выбран Windows Sandbox: тест подтверждает отключённые network, clipboard/audio/video и printer redirection (либо документированное отсутствие канала), единственный необходимый input смонтирован read-only; неподдерживаемая редакция Windows или невозможность принудительно отключить канал закрывает запуск parser job.
19. Запуск isolated-processing требует отдельного аутентифицированного разрешения parser-run, ограниченного hash, форматом и версией адаптера; это право не выводится из права review/release и не снимает quarantine.
20. При выборе Windows Sandbox конкурентные untrusted parser jobs сериализуются; после каждого задания гостевой экземпляр закрывается и удаляется, затем запускается новый. Внутренний reboot не считается сбросом. Тест доказывает отсутствие смешения input/output/scratch; если это нельзя обеспечить, параллельный job отклоняется или выбирается backend с отдельными средами.

## 10. Этапы и критерии допуска

1. Утвердить open decisions; преобразовать этот документ в READY требований с приоритетом,
   владельцем, зависимостями и измеримыми критериями.
2. Безопасная схема provenance, классификации, identity и доступа до публикации проектных
   записей или включения межпроектного поиска restricted data.
3. Dual-query preflight и receipts; локальный и общий результат сохраняют независимый provenance.
4. Локальная запись и контролируемая promotion очередь с отзывом и устареванием.
5. Capability matrix и безопасный ingestion форматов по одному классу; масштабировать поиск
   только после benchmark.
6. Отдельный агентский control plane; подключать knowledge retrieval через проверенный broker.
7. Перед каждой фазой отдельная задача, tests, threat review и readiness gate.

## 11. Неутверждённые решения, блокирующие READY

- какая аутентифицируемая идентичность отличает владельца, Codex, локальных и внешних агентов;
- какие project-confidential сведения допускаются в общей БЗ, на каких устройствах и кому;
- какие классы данных разрешено хранить в GitHub Knowledge_Base и облачной синхронизации;
- требования к шифрованию данных at rest отдельно для канонических записей, оригиналов, производных файлов, индексов/inbox и резервных копий; модель владения/хранения ключей, ротация, восстановление, переносимость, поведение при недоступном ключе и область шифрования. Шифрование архивов с пользовательским паролем не решает этот вопрос; шифрование at rest сейчас не реализовано и политика не выбрана;
- точный baseline расширений, вариантов форматов и минимальных capability для каждого класса; поведение для шифрования, макросов, вложений и неизвестных типов;
- одобренный перечень notebook, analytics, BI/dashboard, diagram и vendor-specific/project packages; форматная схема по одной строке на расширение/вариант с capability и тестовым corpus;
- поддерживаемые файловые системы: local NTFS, removable, UNC/network и sync-managed folders;
- число активных процессов/устройств, writer/broker/CAS, idempotency, conflict/review, lease и crash-recovery semantics;
- реализация parser isolation на поддерживаемых редакциях Windows и других ОС, принудительное network denial, secret isolation, filesystem-safe no-follow/TOCTOU защита и quotas; Windows Sandbox не выбран как универсальный backend и не поддерживается Windows Home. Он допускает только один запущенный экземпляр и является общей средой; при выборе WSB утвердить serial single-job broker, который закрывает/удаляет гостя после задания и запускает новый, либо другой backend с отдельной изоляцией. Проверять отключение сети, clipboard, audio/video, printer redirection и read-only mapping только необходимого input;
- отдельные аутентифицируемые права parser-run, review и release, их область, отзыв и аудит; authenticated quarantine-release receipt; правила обработки паролей, временного plaintext и retention;
- предельные объёмы корпуса/одного файла, число проектов, latency/cancel targets и стоимость OCR/ASR;
- кто принимает promotion, при каких категориях допустим будущий автоматический admission;
- retention, backup RPO/RTO и права на полученные из OSINT документы/медиа.
