# Техническое задание: Development Folder V2

**Версия:** 0.1.0-draft
**Статус:** DRAFT — продуктовая реализация не допущена
**Владелец:** Sc0ch
**Главный ИИ текущего этапа:** Codex
**Дата:** 2026-11-14

## 1. Цель
Создать переносимый эталон и воспроизводимый процесс для будущих самостоятельных программных продуктов: web, SaaS, сайты и панели, API и фоновые службы, аналитика и работа с данными, мобильные и desktop-приложения, CLI и интеграции.

## 2. Границы
Эталон задает структуру, шаблоны, проверки и документацию. Он не устанавливает каждый SDK на хост, не содержит код будущих продуктов и не объединяет разные продукты в один репозиторий. Профили включают только инструменты выбранного проекта.

## 3. Требования
- FR-001 (P0): Чистый шаблон не содержит прикладной код, секреты, локальные базы, пользовательские данные или историю старого эталона.
- FR-002 (P0): Для каждой задачи поддерживается точная зона файлов и изолированная ветка/worktree; посторонние изменения блокируют сдачу.
- FR-003 (P0): main защищена PR-правилом; для PR выполняется неподлежащее пропуску quality-gate с неизменяемой идентификацией SHA.
- FR-004 (P0): Gate проверяет скрипты и конфигурацию эталона, известные утечки секретов, GitHub Actions и формат diff. Скипы и непокрытые профили показываются отдельно от успеха.
- FR-005 (P1): Проектные профили покрывают распространенные серверные, web, mobile, desktop, data/ML и инфраструктурные стеки без принудительной установки всех инструментов.
- FR-006 (P1): Для каждого активного стека задаются поддерживаемые версии, lockfiles, совместимость, тесты, SBOM и проверка известных уязвимостей.
- FR-007 (P1): Документация объясняет локальную разработку, GitHub flow, обновление toolchain, восстановление и передачу работы.
- FR-008 (P1): Прогресс будущего проекта рассчитывается по утвержденным требованиям и критериям приемки с прозрачными весами, остатком, оценкой времени и фактическими данными.
- FR-009 (P1): Локальная база знаний подключается явно и безопасно, а недоступный указанный источник не подменяется другим.
- FR-010 (P1): Проверяется доступность и совместимость toolchain согласно матрице проекта, а не только актуальность каждой отдельной версии.

## 4. Нефункциональные требования
- NFR-001: Безопасность по умолчанию, минимальные права, отсутствие секретов в Git и логах.
- NFR-002: Gate повторяем на Windows в PowerShell 7; будущая поддержка Linux/macOS вводится отдельной проверенной матрицей.
- NFR-003: Документы отделяют факт, предположение, пропуск, неприменимость и неизвестное состояние.
- NFR-004: Все важные решения и версии источников проверяемы по официальной документации и зафиксированной дате.
- NFR-005: Bootstrap должен работать для публичного репозитория GitHub Free без обязательной платной функции.

## 5. Приемка
- AC-001: Чистый checkout проходит базовый gate.
- AC-002: Любой PR вызывает обязательную работу quality-gate даже если меняется только документация.
- AC-003: main не принимает обычный прямой push после начального создания и не принимает force push или удаление.
- AC-004: PR нельзя слить до успешного обязательного CI на merge-result commit, связанном с конкретными PR head и base SHA.
- AC-005: Скрипт/тест, завершившийся ненулевым кодом, блокирует gate.
- AC-006: Неизвестный стек/отсутствие проектного профиля отображается как NOT COVERED, не PASS.
- AC-007: Изменения вне зоны задачи обнаруживаются до публикации.

## 6. Решения и открытые вопросы
- Решение: repository V2 остается публичным по выбору владельца для бесплатного плана; запрещено помещать в него секреты и частные данные.
- Решение: только squash merge; branch protections и GitHub Actions настроены через API и проверяются обратным чтением.
- Открытый вопрос: точный формат генерации проектов и каталога профилей.
- Открытый вопрос: ОС для будущих проектов помимо Windows.
- Открытый вопрос: схема прогресса и оценка оставшегося времени.
- Открытый вопрос: подключение основной базы знаний и ее API/ACL/аудит.
- Открытый вопрос: границы обязательных проверок по классам проекта и планам размещения.
- Открытый вопрос: требования к backup, release signing, SBOM и provenance.

## 7. Допущения и риски
Первичный эталон поддерживает Windows/PowerShell. Инвентаризация SDK и исследование стеков запланированы после фиксации требований. Глобальный каталог языков не заменяет проверку EOL, лицензий, совместимости и доступности на платформе.
