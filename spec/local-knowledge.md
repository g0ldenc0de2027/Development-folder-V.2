# RULES и локальная база знаний: первый рабочий срез

Версия: 0.3.1. Дата: 2026-11-19. Автор: OpenAI Codex, GPT-6.
Статус требований: READY для ограниченных срезов T-004 (LKB-001–008), T-014 (LKB-009 и corrective completion LKB-001) T-031 (LKB-010) и T-032 (LKB-011).
Реализация, проверки и приёмка: отдельно в карточке задачи.

## Основание и допуск

Владелец поручил написать RULES по согласованным решениям и сразу создать локальную БЗ,
затем явно выбрал новую реализацию в Development Folder V2. Эти указания от 2026-11-15
разрешают этот срез. READY не распространяется на весь продукт или будущий рой.

## Границы

Входит: рабочий регламент, Markdown-знания с JSON-каталогом; локальные check/search/get/context,
doctor подключения общей БЗ, capture в ignored inbox; документация и отрицательные проверки.
Исполнение: проверенная Windows 11 x64 GA 26H2/build 26300 на ветке `ge_release` из `config/runtime-support.json` и PowerShell 7.6 LTS не ниже 7.6.10; стандартная библиотека, без новых зависимостей. Hosted CI выполняет отдельную проверку на Windows Server 2025 x64 build 26100.

Не входит: автоматическое принятие знаний, издатель общих правил, миграция V1,
полноценный поиск общей БЗ, embeddings/SQLite, API/MCP/UI, dispatch роя,
аутентификация reviewer, защита от процесса с unrestricted shell той же учётной записи.
Публичный репозиторий содержит только разрешённые проектные знания.

Уточнение владельца: одновременно подготовить новую общую БЗ в указанном им месте.
Местоположение произвольное, в том числе другой диск; путь не является константой.
Входит создание пустого общего корпуса того же формата, исходного канона RULES и
project policy-lock с SHA-256. Редактируемый канон только общий; обновление копий пока
ручное, без authenticated publisher и автоматического контроля remote freshness.

Уточнение владельца от 2026-11-16: общая БЗ получает выбранные ценные знания из локальных БЗ всех проектов и прямые записи владельца на любую тему; при работе сначала проверяются общая и проектная БЗ. В целевой портфельной модели проектная запись должна сохранять origin, точную ревизию, scope, classification и audience. Это целевые метаданные, а не текущая реализация: schema 1 сейчас хранит только id, kind, title, status, path, contentSha256, sources и review; per-record origin/scope/classification/audience и ACL-фильтрация отсутствуют. До их реализации и проверки нельзя помещать закрытые/project-confidential записи в общую Git-backed коллекцию. Локальный источник остаётся подробным источником истины проекта.

На старте содержательной задачи обязательна проверка локальной и общей БЗ. При недостатке актуальных сведений тяжёлый случай проходит OSINT/Deep Research и профильную экспертную проверку по правилу 20. После работы выводы сохраняются локально; важные для портфеля или указанные владельцем знания предлагаются в общую после проверки. Это требование к процессу, а не заявление об уже реализованной федерации или publisher.

Полный целевой lifecycle, контроль доступа, agent workflow и file capability matrix описаны в spec/portfolio-kb-agent-workflow.md со статусом DRAFT / NOT READY. Текущий CLI по-прежнему проверяет и ищет только одну коллекцию за вызов, без межпроектных ACL и promotion. Доступ к restricted project data нельзя обосновать одним фактом нахождения файла в общей БЗ.
Уточнение владельца от 2026-11-16: обе базы должны уметь хранить и обрабатывать основные
типы файлов. Текущий T-004 реализует только Markdown-записи и JSON-каталог: универсальное
хранилище оригиналов, извлечение Office/PDF, OCR/ASR, архивный карантин и единая матрица
возможностей не реализованы. Это целевое требование обеих баз, не приёмочный критерий
ограниченного T-004; перед реализацией нужен отдельный READY-спек с форматной матрицей,
границами хранения, безопасной обработкой и acceptance criteria.

## Уточнение среза: модульные правила

Повторное поручение владельца от 2026-11-15: сверить правила с прежним регламентом
и замечаниями аудита. Допуск READY включает строго фиксированный пакет из девяти файлов:
`rules/RULES.md`, семь канонических модулей `rules/modules/01-knowledge-and-calibration.md`,
`02-spec-and-quality.md`, `03-agents-and-workspace.md`, `04-git-and-release.md`,
`05-security.md`, `06-ui-i18n-help.md`, `07-research-and-decisions.md` и `rules/COVERAGE.md`.
Policy-lock schema 2 фиксирует каждый файл; CLI требует точное множество этих путей и
отклоняет неполный, подменённый или расширенный список кодом `KB_POLICY_LOCK`, даже если
индекс не ссылается на модули. Ссылка на не включённый в lock файл отклоняется как
`KB_POLICY_LINK`. Схема каталога знаний
остаётся 1. Schema 1 policy-lock не активируется: заменить полным проверенным пакетом
одной задачей, сохранив исходный снимок. Неполная поставка должна вызвать отказ.
Context возвращает все закреплённые тексты; их нельзя молча урезать по бюджету.
Обязательный контракт: номера 1–20 без потерь; locale IDs ru/en/zh-Hans/hi/es/ar/fr/bn/pt-BR/de.
Doctor допускает отсутствие/null knowledge_base; нестроковое значение — ошибка.
Это не допуск к реализации UI, security-watch или всех стековых проверок.

## Данные, доверие и безопасность

Канон содержания — Markdown; catalog — канон метаданных той же записи. Оба в Git.
JSON разобран строго: duplicate keys, неизвестные поля/версии и недопустимые типы — ошибка.
Проверка hashes подтверждает целостность, а не истинность или identity reviewer.
Все начальные записи имеют draft. Проверка/принятие знаний — отдельное действие главного ИИ
с evidence; CLI этого среза не выдаёт полномочий publisher.

Inbox — data/knowledge/inbox, вне Git. Это локальные рабочие предложения; их нужно
резервировать, если потеря недопустима. Сканер очевидных секретов не гарантирует очистку.
Реальные secrets/PII туда не записываются. Read/capture не обращаются к внешним моделям.
Reparse checks сокращают риск; не обещают OS sandbox или защиту от всех TOCTOU атак.
CLI допускает только локальный fixed/removable volume с известной Windows ФС. Корень проекта и каждый существующий компонент пути от корня тома проверяются на reparse point до определения volume, чтобы родительская junction не подменила проверяемый том. Для `knowledge/catalog.json`, записей `knowledge/records/*` и `.etalon.json` на NTFS/ReFS/UDF каталоги до 24 записей сначала проверяются `fsutil hardlink list`; больше 24 — сначала числом links через `GetFileInformationByHandle` на открытом handle. Если выбранный способ не может получить полный достоверный результат, CLI однократно пробует альтернативный способ: native-проверка принимает только link count 1, `fsutil` — ровно один путь, совпадающий с проверяемым. Несколько дают `KB_HARDLINK`; если оба способа недоступны или неоднозначны — `KB_LINK_ENUMERATION_UNAVAILABLE`. FAT/FAT32/exFAT не поддерживают hard links и не требуют перечисления. Сетевые и неизвестные типы/форматы томов блокируются. Закреплённые правила отдельно проверяются по SHA-256 lock. Проверка снижает риск существующего alias, но не является OS isolation и не исключает гонку создания alias после проверки.

## Наблюдаемость, восстановление и эксплуатация

CLI: JSON stdout, диагностический код stderr, ненулевой exit при ошибке.
Вывод не содержит исходного текста ошибки парсинга/секрета. Captured receipt возвращает ID.
Канон восстанавливается из Git и отдельного backup незакоммиченного; inbox — отдельно.
Никакой автоматической activation старого restore или переноса live sessions.

## Решения и открытые вопросы

Решено: основной ПК/offline/переносимость, наружу только разрешённые данные;
GitHub-доноры дают идеи, реализацию пишем сами; общий канон правил выбран целевой архитектурой;
локальная БЗ проектная, общая БЗ портфельная по owner clarification 2026-11-16; обе базы должны получить обработку основных типов файлов, пока это не реализовано.
Первичная редакция правил готовится по текущему поручению и помещается в общую БЗ;
V2 получает побайтную копию и lock. Полноценный publisher и отзыв поставок остаются вне среза.
PowerShell здесь — ограниченный первый CLI, а не окончательный выбор ядра роя.
Открыто вне среза: publisher/lock протокол, backend индекса, adapters и OS isolation.

## LKB-010 — Компактный поиск

Явный `search -Compact` использует те же совпадения, порядок, статусы и счётчики, что и полный поиск. Объект результата добавляет `representation: compact`; запись содержит только `id`, `kind`, `title`, `status` и `contentSha256`. Поиск по телу сохраняется. Флаг для другой команды возвращает `KB_COMPACT_SEARCH_ONLY`. Бюджет `MaxOutputBytes` применяется к итоговому JSON с LF. Потребление памяти при чтении корпуса остаётся отдельной задачей.

Приёмка: поиск по телу на кириллице, совпадение карточки с полным результатом и get, исторические и пустые выборки, граница бюджета, отказ для другой команды и при нарушении целостности.

## LKB-011 — Проверка ID выбранной коллекции

Для check/search/get/context необязательный ExpectedCollectionId сверяется с ID того же каталога, который используется в текущем вызове. Формат совпадает с projectId каталога: ненулевой UUID формата D, регистр не влияет на сравнение. Неверный формат возвращает KB_EXPECTED_COLLECTION_ID_INVALID, несовпадение — KB_COLLECTION_ID_MISMATCH, отсутствующий корень — KB_ROOT_UNAVAILABLE. Флаг на других командах возвращает KB_COLLECTION_ID_READ_ONLY. Отказы возвращают exit 1 и пустой stdout. Проверка действует до чтения тел записей, работает при переносе корня и не удостоверяет издателя. Без параметра действует существующий контракт.
