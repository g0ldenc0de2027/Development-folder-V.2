## Критерии приёмки

1. Исследование фиксирует метод, дату, direct URLs и точные SHA выбранных GitHub источников; отдельно маркирует official facts, README/ADR claims, выводы и неизвестное; не заявляет полный market/source audit.
2. Аналоги сравниваются по функциям, отказам, безопасности, платформенной применимости и пригодности для нашего сценария; указано, что заимствовать как идею, что не переносить и почему.
3. Матрица агентов различает поставщика, точный продукт и поверхность, hosting/execution location, runtime/build, аккаунт/plan-класс, модель, официально заявленные capabilities, owner-observed настройки и фактически протестированные операции. Отдельно фиксируются auth, data path, egress, history/memory, tools, permissions, retention, cost evidence и ограничения Windows. Документация подтверждает только заявление производителя; owner observation — только видимые настройки выбранного профиля; SUPPORTED для операции требует runtime-теста точной поверхности/build. UNKNOWN не считается готовностью. GitHub-доноры имеют точные pins и маркировку source/README evidence.
4. Спецификация задаёт цель, границы, role/capability permission matrix, task/run/review/integration state machines, guards и terminal semantics, late/duplicate/unknown/reconcile; review_generation и review_phase привязаны к точному target tuple и CURRENT-only aggregation. Egress связывает transport, surface, thread, account memory, отдельные account-level instructions/cross-chat history и digest каждого активного содержимого и evidence, retention, clipboard exposure; неизвестное состояние блокирует M1, а ENABLED_FULLY_REVIEWED требует полного preview и digest binding. Resume разделяет read-only observe/reconcile прежней operation и новую continuation/dispatch, сохраняет run/session/operation binding и никогда не возобновляет неизвестный внешний эффект вслепую. Handoff различает copy/export, owner-reported dispatch и provider receipt; integration proposal guard разделяет INITIAL_INTEGRATION/REMEDIATION и запрещает нормальное закрытие task при любой связанной нетерминальной proposal; снятие assignment отзывает permits и блокирует stale dispatch; заданы one-shot approval binding, event/store contract, KB/Git separation, Windows threat model, отрицательные тесты, recovery и open decisions.

## Рабочие решения для проектирования

- Одна активная координаторская роль на проект/рабочий поток; смена руководителя — явная передача полномочий и новый epoch.
- Рабочая доска — источник истины о задачах/запусках/результатах; локальная БЗ — память конкретного проекта; общая БЗ — отобранная портфельная память; Git — история кода и ревью. Чаты не являются журналом состояния задачи.
- Codex — текущий главный ИИ по решению владельца. Состав первого набора: Codex, ChatGPT (второй аккаунт), Antigravity, Kimi, Xiaomi MiMo, Qwen Code CLI, Tencent WorkBuddy и DeepSeek. Этот перечень не доказывает наличие API/CLI или успешную аутентификацию.
- Первая версия не исполняет команды агента и не предоставляет ему файловую запись. Ручные передачи тоже считаются внешней передачей данных и требуют предпросмотра и минимизации.
- Стек приложения и окончательное место базы координации остаются открытыми; SQLite рассматривается как кандидат для локального прототипа, не как утверждённый выбор.
