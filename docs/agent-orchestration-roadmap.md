Дополнительное условие выхода M1: golden fault-injection сценарии из spec/agent-orchestration.md §§8 и 12 доказывают, что повреждённый store не затирается, approval и локальная мутация согласованы атомарно, неизвестный внешний эффект не превращается в повторный запуск, а второй writer не может мутировать состояние в обход single-writer ограничения. ## Архитектурные решения, отложенные до evidence

- **M1 остаётся owner-mediated.** Одна локальная доска и один writer; никакого автоматического запуска перечисленных провайдеров, direct agent-to-agent calls, file access, shell, Git write, MCP server или auto-publish. Эти запреты описывают целевой scope, а не реализованные/проверенные controls; продукта и enforcement пока нет. Новая система хранит состояние задач и handoff evidence; project/shared KB остаются раздельными источниками знаний по утверждённой модели.
- **Неизвестная стоимость блокируется по умолчанию.** M1 не выдаёт EgressPermit при cost UNKNOWN, пока владелец не утвердил исключительную M0 policy. Если policy разрешает ручное продолжение, owner acknowledgment одноразово связан с точным permit/package/provider profile и digest cost snapshot, валютой/периодом и ceiling либо явным UNBOUNDED_UNKNOWN_ACCEPTED. Это согласие не ограничивает расходы технически внутри внешнего UI; автоматический dispatch требует доказуемого hard cap и остаётся закрытым при его отсутствии.
- **Не показывать неподкреплённые метрики.** M1 не публикует процент/ETA; M2 считает owner-accepted deliverables относительно версионированного полного baseline с утверждёнными весами; при малой истории ETA = NOT_ESTIMABLE, scope changes требуют прозрачного rebaseline. Usage/cost показывает сумму только с evidence state, валютой и периодом; UNKNOWN не превращается в ноль. SQLite — кандидат на локальный store, workflow frameworks/brokers/vector DB не входят в M1. Перед выбором обязательны измеримый workload, crash/restart test, backup/restore drill и проверка блокировок/расположения data-root.
- **M3 и M4 — отдельные допуски.** M3 остаётся passive registry без запуска процесса/подключения к workspace; обязательные conformance cases фиксируют отдельные исходы, а SKIPPED/NOT_TESTED оставляют capability UNKNOWN и блокируют маршрутизацию. TCK не является security certification. M4 допускается только отдельной READY security specification, Windows host capability preflight, OS-enforced boundary, egress default-deny, секретов вне образца, bounded stdout/stderr, negative tests и независимого security review.
- **Сравнить изоляцию, не доверять бренду.** CLI-only synthetic pilot: Quicksand против Docker Sandboxes; проверить guest-to-host channel, host mounts, SSH/MCP credentials, process-tree cancellation, crash/restart и network denial. GUI-only пилот — отдельная Windows VM. Windows Sandbox применим лишь для disposable сценария с выключенными сетью/clipboard/vGPU и read-only narrow mount. NVIDIA OpenShell Windows branch на pinned snapshot — не production boundary. До такого пилота инструменты не являются выбранной архитектурой.
- **Telemetry privacy by default.** Сначала фиксируются минимальные correlation IDs/status/aggregates. Raw prompt, response, memory, attachment и tool args выключены до отдельного решения о redaction, retention и доступе.
- **Отмена внешнего действия не означает отмену эффекта.** На M5 dispatch-claim и owner cancellation должны быть атомарно упорядочены; до claim — доказанный no-effect, после claim — best-effort cancel, UNKNOWN/reconciliation при неопределённом исходе, без слепого retry.

Ни одна строка roster не означает выбранный или проверенный runtime profile; ручной MVP допускает профилированное подмножество, а не автоматическую доступность всех названных продуктов.

## Блокирующие ограничения

- Нельзя считать наличие CLI доказательством авторизации или sandbox. cwd, worktree, ACP/MCP и Job Object сами по себе не обеспечивают filesystem/network confinement.
- WorkBuddy snapshot показывает Network error только в момент снимка; повторить проверку перед назначением.
- Ни при каких заявленных permissions внешнее приложение на M1 не получает live checkout, project root, .git, local KB/data-root или credentials. M1 egress допускается только на owner-verified passive ordinary surface без tools/connectors/actions/scoped knowledge, с attested new empty thread и verified disabled account memory; transport method входит в approval binding; clipboard history/sync/manager/shared clipboard UNKNOWN или ENABLED блокирует все классы, а SENSITIVE/CLOSED clipboard запрещён независимо от профиля; UNKNOWN/active surface, tools, thread history или account memory блокирует все payload, включая public. UNKNOWN только retention может разрешить public/non-sensitive исключительно по явной M0 policy. Workspace access требует отдельной READY capability и OS boundary.
- M4 не опирается лишь на prompt, Git worktree или добросовестность модели.
- M5 требует отдельные INITIAL_INTEGRATION и REMEDIATION proposal с guard по ACCEPTED/BLOCKED состоянию; независимый review и CI на точном SHA, а также отдельного одноразового owner approval на конкретную операцию; auto-merge вне объёма.
- Общая KB — источник поиска; publisher и автоматическая синхронизация не реализуются этой дорожной картой.

## Правило остановки

Вернуть этап в дизайн, если неизвестны получатель/контекст, результат операции после сбоя, полномочия процесса, восстановление, точный review SHA или фактический охват gate. Не скрывать это общим статусом «готов».

Следующий шаг: получить свежее независимое read-only review точного нового snapshot по owner-approved M0 review_policy, cross-vendor только если policy его требует; затем закрыть решения владельца M0 из раздела 10 спецификации. До READY разрешена работа над DRAFT-документацией и исследованием; реализация и внешние автоматические вызовы не допускаются.
