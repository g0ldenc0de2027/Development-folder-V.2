## Правило 14. Безопасность и данные

Минимальные права, безопасные defaults, threat model для существенных data/tool effects.
Secrets и личные данные не попадают в Git, знания, prompts и logs. В примерах — синтетика.
Доступ к файлу не разрешает отправку любому провайдеру. Локальная обработка по умолчанию;
egress разрешается явно по данным, цели и получателю.

Зависимости: проверенный источник, поддержка, lock, известные vulnerabilities и license.
Карантин новых dependencies — семь дней, кроме обоснованного security fix;
install scripts разрешаются поштучно. Не импортировать код GitHub-доноров:
по решению владельца используем идеи и пишем реализацию сами.

Критическую/эксплуатируемую уязвимость разбирать немедленно, до новой функции;
фиксировать affected scope и необходимое исправление. Сроки иных рисков — по тяжести.
Hash, readonly flag, worktree и localhost не создают OS sandbox.

Backup отделён от sync. Restore сначала staging и проверка актуальных прав/отзывов.
Уже отправленный внешней модели текст нельзя технически вернуть из её контекста.

### Подключение проверки безопасности

Для каждого проекта отдельно определить источники, стек, доверенные команды и допустимые
эффекты сканирования. Security-watch onboarding фиксирует согласованный project ID,
корень, config/command revision и разрешение на запуск. Изменившийся исполняемый
профиль требует повторной проверки; до этого проект NOT COVERED.
В V2 security-watch ещё не установлен. Старый scheduler и approval из V1 не переносятся молча.

Публичный web/API требует применимых проверок injection/XSS/CSRF/SSRF/auth/rate limits;
для SaaS/платежей/PII — threat model, isolation, audit и проверка recovery.
SAST, dependency scan, SBOM и DAST покрывают разные угрозы. Автоматический scanner
не заменяет целевое security review и не даёт гарантии отсутствия взлома.
Pentest/red-team запускается только в разрешённом scope.
