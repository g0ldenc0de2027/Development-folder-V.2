# Требования, качество и прогресс

Редакция 0.2.0 · 2026-11-15 · Codex, gpt-6.1-sol.
Область и приоритет — [RULES](../RULES.md). Это нормативный текст, не отчёт о реализации.

## Правило 2. Минимум необходимого процесса

Для обычной задачи достаточно ясного scope, одной карточки, результата и применимых
проверок. Новый реестр или approval добавляется только ради конкретного предотвращаемого сбоя.
Уже выданное разрешение не запрашивается повторно в прежних границах.

Независимая работа продолжается при локальном блокере другой задачи.
Не проводить новый полный аудит после каждого исправления без причины.
Обнаруженный существенный риск не скрывать ради скорости.

Не удалять записи по одному возрасту. Сжимать только утратившие актуальность сводки,
сохраняя ссылки на решения и открытые действия; чужие данные — с разрешения владельца.
Не создавать искусственные документы ради формального compliance.

## Правило 3. Профессиональное качество и честная готовность

Результат соответствует согласованной задаче, запускается в поддерживаемой среде,
понятен пользователю и сопровождается нужными инструкциями.
Премиальное качество означает надёжность, безопасность, удобство, доступность,
поддерживаемость и измеренные характеристики, а не количество функций или документов.

Перед сдачей проверить полный diff, применимые требования и негативные сценарии.
Отчёт различает PASS, FAIL, SKIP, NOT COVERED, NOT APPLICABLE.
Неизвестный стек, пустой профиль и зелёная оболочка не подтверждают безопасность приложения.
Критический непокрытый сценарий блокирует соответствующее обещание готовности.

### Измеримые требования из утверждённого регламента

| Проверка | С1 | С2 | С3 |
|---|---|---|---|
| Форматтер/линтер/строгие типы | 0 замечаний | 0 | 0 |
| Покрытие ключевой логики | >=70% | >=80% | >=90% |
| Мутационное тестирование ядра | По риску | По риску | >=60% |
| Уязвимости | 0 критичных/высоких | 0 средних и выше | 0 средних и выше |
| SBOM | По применимости | Обязателен | Обязателен |
| Доступность UI | WCAG 2.2 AA | WCAG 2.2 AA | WCAG 2.2 AA |
| Веб LCP / INP / CLS | <=2,5с / <=200мс / <=0,1 | То же | То же |
| Старт desktop/mobile | <=2с | <=1,5с | <=1с |

Порог применяется к согласованному объёму и измеренному окружению.
Coverage не заменяет проверку критических сценариев. Неизвестная severity не равна нулю рисков.
Исключение из обязательного порога требует владельца, причины и compensating controls.
Таблица — нормативный target. В V2 она пока не реализована как матрица всех прикладных
профилей: недостающая обязательная команда остаётся NOT COVERED/блокером соответствующей сдачи.
Текущий bootstrap gate не подтверждает coverage/SBOM/DAST будущего приложения.

Для каждой нормы см. COVERAGE: механизм, охват и оставшийся пробел.
Свидетельство проверки содержит команду, версии, дату, среду, SHA/хэш, результат и ограничение.

## Правило 13. Класс, прогресс и сроки

ТЗ определяет сложность, аудиторию, нагрузку и риск; профиль задаёт применимые gates.
Процент считается по утверждённым требованиям/пакетам с весами и evidence.
Отдельно показывать сделано, осталось, blocked, непроверенное и release readiness.
Не выводить готовность из числа файлов, commits, токенов или сообщений агентов.

ETA содержит предположения о мощности команды, critical path, диапазон неопределённости
и ожидание review/ответов. Уточняется по фактическим этапам; не обещать дату без основания.

### Классификация

С1 — одна небольшая задача/локальные данные; С2 — несколько модулей, роли/БД/API;
С3 — несколько сервисов, SaaS/multitenancy, платежи или высокая надёжность.
Уровни пользователей: П1 1–10, П2 11–100, П3 101–1000, П4 более 1000.
В ТЗ указываются зарегистрированные и активные за день; оценить данные и нагрузку отдельно.
Малое число пользователей не снимает рисков платежей/PII; число регистраций само не требует кластера.

Ориентиры при отсутствии иных утверждённых: отклик UI <=100мс, открытие экрана <=1с,
API p95 <=300мс при согласованном пике. Для долгой операции — прогресс и отзывчивый UI.
Метод измерения, устройство, объём данных и concurrency фиксируются до сравнения.

## Правило 18. Требования до реализации

Новая возможность имеет scope/out-of-scope, требования с IDs, зависимости и acceptance.
Применяется technical-specification-architect. READY выдаётся только определённому срезу;
готовый инфраструктурный этап не открывает всё ТЗ.
Поведение изменилось — требования и docs обновляются вместе с кодом.
Исправление без изменения согласованного поведения не требует нового большого ТЗ.

ТЗ содержит факты, допущения, решения и открытые вопросы, приоритеты, scope/out-of-scope,
данные/API, риски, UX, безопасность, эксплуатацию и проверяемые критерии в нужной глубине.
С1/П1 — короткий паспорт; более сложным проектам нужны дополнительные проходы.
Прототип рискованной идеи допускается в явно согласованных границах, без права выпуска.
Обновлять документацию текущего среза в той же задаче; unrelated unknowns не блокируют
самостоятельный принятый объём, если для него нет материального риска.
