## Цель и решения владельца

Нужен процесс, где ведущий ИИ принимает задачу владельца, уточняет её, делит на проверяемые подзадачи, назначает исполнителей, передаёт только нужный контекст, принимает результат, возвращает на исправление и интегрирует принятую работу. Владелец остаётся главным источником полномочий.

Начальный набор: Codex, ChatGPT со второго аккаунта, Antigravity, Kimi, Xiaomi MiMo, Qwen Code CLI, Tencent WorkBuddy и DeepSeek. WorkBuddy уточнён как Tencent WorkBuddy, исполнитель Qwen — как Qwen Code CLI. Список — целевая совместимость, не доказательство доступности API, авторизации, запуска или права работать с файлами.

Владелец выбрал первую версию как локальную доску и ручную передачу. Это не разрешает автоматический вызов CLI/API, выполнение команд, запись в проект, публикацию в GitHub, автослияние или изменение общей БЗ.

## Рекомендация

**MVP: локальная board + ручное подтверждение и передача.** Так система уже согласуется с разнородными UI и не притворяется, что у всех есть общий API. Позже — по одному адаптеру после отдельной проверки.

Один coordinator на поток; сейчас Codex. Передача роли фиксируется отдельным событием и возрастающим epoch, чтобы поздний ответ прежнего лидера нельзя было принять как актуальный. Worker получает одну ограниченную задачу. Reviewer не является исполнителем проверяемого изменения. Coordinator готовит предложение интеграции, но в MVP не исполняет его: изменения в файлы/Git выполняет владелец. Будущий названный executor допустим только после отдельной одноразовой owner approval, привязанной к точному действию и diff; merge/release и публикация знаний остаются отдельными решениями владельца. «Общение» означает адресные пакеты и отчёты через доску, без самостоятельной неограниченной peer chat.

Task, run, review и integration имеют отдельные lifecycle; канонические transition tables и guards описаны в spec/agent-orchestration.md `4, FR-AOR-004. Review verdict — поле результата, не состояние; freshness проверяется отдельно по digest/base/policy. Integration proposal не равно owner approval, а approval — не исполнение. Нажатие, отправка, ответ, проверка, принятие и интеграция — разные события; неизвестный исход не считается успехом.

Пакет задания несёт ID/revision, цель, критерии, получателя, coordinator epoch, base SHA при изменениях кода, read/write set, минимальный контекст с источниками, data classification, формат ответа, тесты, запреты, лимиты, expiry/nonce и версию правил. Перед отправкой — точный preview текста/вложений/получателя и явное подтверждение. Запрещены секреты, .env, личные данные, рабочие базы и неразрешённые закрытые сведения. Ручной ответ хранится вместе с источником и помечается MANUAL_UNVERIFIED; заявления о тестах проверяются локально.

Board — текущее операционное состояние, local KB — долгоживущие знания проекта, shared KB — отобранные знания портфеля, Git — код и review. Не хранить временную очередь в KB. Будущее хранилище — вне Git, на выбранном локальном data-root; сетевое/cloud синхронизирование live DB требует отдельной модели согласованности. SQLite — кандидат для spike, не принятое решение.

## Security и reliability baseline

В целевом scope M1 запрещены shell, write access, Git push, auto-merge, API calls и arbitrary MCP servers; это требование, а не реализованный контроль, поскольку продукт ещё не создан. Внешний egress в target design запрещён до точного preview и owner approval; enforcement не проверялся. Входные файлы, сайты и отчёты — недоверенные данные. Loopback listener в будущем требует auth, CSRF/Origin защиты и безопасного bind; localhost не boundary. Git worktree не sandbox и не скрывает .git, home profile, credentials или сеть. До сохранения чувствительных prompt/transcripts нужно решить at-rest encryption, keys, backup и retention.

Будущие негативные тесты: выход за write-set; absolute path/junction; inherited credentials; запрещённая сеть; неверный получатель; prompt injection; replay/старый epoch/base SHA; дубль; network timeout; ложная отмена/заявление о тестах; crash между состояниями; повреждение/restore. Run ограничен итерациями, временем и бюджетом при наличии достоверных сигналов. Результат unknown/timeout не запускает автоматический повтор без проверки дубликата.

Прогресс строится по заранее утверждённым deliverables: planned, claimed, verified, accepted. Без весов нет процента. ETA — диапазон с неопределённостью на основе истории; время ожидания внешнего агента отдельно от активной работы. Метрики: first-pass acceptance, возвраты и severity, queue/dispatch/wait/active/review time, unknown/duplicate/cancel rate, проверяемость тестовых заявлений, непреднамеренный egress (цель 0), потеря/сбой восстановления (цель 0).

## Этапы и открытые решения

- M0: READY decisions — поддерживаемая Windows, data classification, interface, storage, backup/restore, encryption, egress и acceptance.
- M1: ручная локальная board, capability registry, event timeline, work-package preview/export, ручной import ответа, ссылки на KB/Git и детерминированный crash/restart replay подтверждённых событий; неопределённый внешний эффект остаётся UNKNOWN без retry.
- M2: полный backup/restore и restore drill, schema migration/rollback, операционная recovery-модель, поиск, accessibility, прогресс/ETA.
- M3: только пассивная запись owner-supplied evidence о версии/протоколе/runtime без запуска или подключения к CLI/provider session, IPC, workspace, файлам или сети. Любое активное наблюдение, даже read-only, — отдельная READY capability с подтверждённой OS boundary и отрицательными тестами.
- M4: isolated write-capable adapters, per-task permissions, egress/cancellation/recovery tests и security review.
- M5: контролируемая интеграция, независимое review и CI на точном SHA; auto-merge не включён.
- M6: multi-PC network только после identity/auth, key management, transport, privacy и recovery design.

До READY решить: Windows baseline; desktop UI или защищённый local web UI; SQLite или иной store; переносимый data-root; шифрование/backup/retention; классификацию данных и список разрешённых получателей; формат ручного импорта; один проект или portfolio view; прогресс/ETA; запасной независимый reviewer.

## Итог и ограничения

Рекомендован путь: сначала локальный операторский центр для ручной координации и пассивная запись предоставленных владельцем capability evidence; любое активное подключение или наблюдение CLI/provider session, даже read-only, допускается только отдельной READY capability после OS-boundary и негативных проверок. Isolated write-capable адаптеры — следующий отдельный допуск. Полностью автономный рой сейчас преждевременен: статусы продуктов и auth неодинаковы, WorkBuddy на снимке показал Network error, а локальная файловая изоляция не доказана.

Статус: CONTINUE_TARGETED_RESEARCH перед READY. Storage, UI, data classification, backup/encryption и security acceptance остаются открытыми. Реализация не начата и этим отчётом не допускается.

### Архитектурный синтез

Разделение: Board/Control Plane → Adapter → Provider Runtime → изолированная Workspace → Evidence/Review → owner decision. В MVP реализуются только durable local board, capability registry, preview/export и manual import. Универсальный API для всех брендов нереалистичен: UI, local CLI, ACP, proprietary App Server и cloud model API имеют разные права и lifecycle.

Будущий adapter объявляет capabilities отдельно: discover, validate, prepare, dispatch, observe, resume, cancel, reconcile, collect_result. У каждой capability статус SUPPORTED/NOT_SUPPORTED/UNKNOWN/DEGRADED, версия/доказательство, дата и expiry. Сохраняются raw provider status/event и session/run ID. Отсутствие resume/cancel — штатный результат; автоматический retry при unknown запрещён.

Для local durability сравнить SQLite с транзакционным event journal и append-only JSONL только в ограниченном spike. MVP: одна машина, один writer, транзакционные команды с version check; backup/recovery проверяются. Live DB в сетевой/cloud-synced папке запрещена до модели consistency. Data-root остаётся переносимым, стек/UI не выбраны.

Будущий worker требует отдельную workspace на run; path allowlist — не sandbox. На Windows исследовать AppContainer/Windows Sandbox; network/clipboard sharing, profile, secrets, .git, hooks и credentials закрыть по умолчанию. Job Objects годятся для process lifecycle/resource limits, но не filesystem/network confinement. При отказе sandbox запуск fail-closed. Junction/reparse point, hard link и race обязательны в negative tests.

Любая ручная передача наружу — egress: preview точного prompt/вложений/provider/account/data class и явное owner approval. Его надо связать с digest payload, адресатом, проектом, сроком и one-time nonce. Изменение любой привязки отзывает разрешение. Результат ручного импорта — MANUAL_UNVERIFIED до независимой проверки.

### Дополнение к threat model и отрицательным тестам

До допуска capability система должна отрицательно проверять: forged/stale actor; изменение payload/recipient/provider/account/target SHA после approval; duplicate event и повтор idempotency key с иным payload; cancel timeout/late response; crash на границах записи; неизвестную schema; SSRF/redirect/local network; утечку через лог/clipboard; доступ к .git/profile/credential store; junction/hard-link/path swap; отсутствие auth; потерю lock/lease; disk/token/process/runtime budget; запрещённую KB promotion; restore старой копии поверх новой очереди. Неисполнение negative case блокирует соответствующий capability.

OWASP Top 10 for Agentic Applications 2026 — карта угроз, а не сертификат. NIST SP 800-162 даёт ABAC vocabulary; агентская identity работа NIST остаётся emerging guidance/concept, не окончательный межвендорный стандарт. Точный механизм identity/authorization остаётся open design.

### Протоколы и границы гарантий

- **ACP** — потенциальный локальный client↔coding-agent protocol. В версии 1 основной transport — stdio; HTTP ещё специфицируется. Сам протокол не создаёт sandbox: agent identity/capability metadata могут быть self-reported, permission requests advisory, а cancellation implementation-specific; поздние события требуют reconcile. [Overview](https://agentclientprotocol.com/protocol/v1/overview), [security](https://agentclientprotocol.com/protocol/v1/security), [transport](https://agentclientprotocol.com/protocol/v1/transports), [cancellation](https://agentclientprotocol.com/protocol/v1/cancellation).
- **MCP** — подключение tools/resources с собственными рисками confused deputy, token passthrough, SSRF и local-server compromise; это не durable board и не общий канал общения агентов. Любой будущий MCP сервер требует отдельной оценки аутентификации, области данных, egress и запуска. [Security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices).
- **A2A** — кандидат для будущих удалённых agent-services только при появлении поддерживаемого сетевого endpoint; не нужен для ручного UI-based MVP и не заменяет локальный task ledger. [A2A v1.0 specification](https://a2a-protocol.org/v1.0.0/specification/).
- **OpenTelemetry GenAI conventions** в закреплённом снимке open-telemetry/semantic-conventions-genai@0c87594975195608dc91b3f702e250a7b240c151 (commit 2026-09-10; источник проверен 2026-11-17) имеют статус Development. Спецификация предупреждает о чувствительности prompt/input/output, memory/retrieved records и tool arguments/results; по умолчанию содержимое не следует писать в telemetry. Для архитектуры применяем отдельную policy, redaction и retention, но статус источника относится только к закреплённому снимку. [Статус и GenAI spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/0c87594975195608dc91b3f702e250a7b240c151/docs/gen-ai/gen-ai-spans.md#L192-L195), [чувствительное содержимое и default](https://github.com/open-telemetry/semantic-conventions-genai/blob/0c87594975195608dc91b3f702e250a7b240c151/docs/gen-ai/gen-ai-spans.md#L1241-L1259), [memory attributes](https://github.com/open-telemetry/semantic-conventions-genai/blob/0c87594975195608dc91b3f702e250a7b240c151/docs/gen-ai/gen-ai-spans.md#L1060-L1069).

### Выводы для архитектуры

1. **Разделить пять авторитетов.** Локальная доска/event ledger — авторитет по задачам, assignments, approvals, attempts и их состояниям; Git — по версии кода/diff; project-local KB — по принятому контексту одного проекта; shared KB — портфельная память и прямые записи владельца с curated promotion; внешние чаты — только поверхности передачи/ответа. Трейсы/метрики объясняют исполнение, но не подтверждают доставку или принятие. Их нельзя сводить в один transcript/status.
2. **Начать с одной Windows-машины и одного writer.** Для M1 сохранить ручную долговечную доску: owner/coordinator создаёт task/run/review generation, показывает точный минимальный пакет, человек вручную запускает и передаёт его выбранному UI, а ответ вручную связывается с task/run и проверяемым digest. Не добавлять workflow framework, broker, vector DB или provider adapters до измеренной потребности. SQLite остаётся кандидатом, не решением; сетевой/cloud-synced live DB исключён до multi-writer consistency design.
3. **Сделать явный recovery-контракт.** Stable task/run/attempt/event IDs, idempotency keys, optimistic aggregate version, durable owner decision, request cancellation отдельно от подтверждённой остановки, поздний/дублированный ответ через quarantine/reconcile. Нельзя обещать exactly-once; при неизвестном внешнем эффекте — DELIVERY_UNKNOWN, reconcile, без автоматического повтора.
4. **Не смешивать память и операционное состояние.** KB хранит проверенные долговременные знания, решения и provenance, не live очередь и не источник task status. В начале substantive work искать в обеих KB; пробел закрывать research по Rule 20; находки писать в project-local KB, а перенос в shared KB оформлять предложением после проверки provenance/freshness/conflict/privacy/security/license/scope/audience. Publisher и federation остаются будущими возможностями.
5. **Сохранить owner-mediated взаимодействие.** M1 не позволяет агентам напрямую вызывать друг друга или писать в доску. Координатор формирует адресные пакеты/задачи, владелец передаёт их внешним продуктам и возвращает ответы; account/model/runtime/provider identity фиксируются раздельно, UNKNOWN остаётся неизвестным. Позднее можно изучить capability-bounded adapters без изменения источника истины.
6. **Развести адаптеры и security enforcement.** ACP/MCP/A2A — разные протоколы и не взаимозаменяемы. Protocol permission, worktree, Job Object, prompt или localhost не доказывают OS isolation. M1 не запускает agent process. Любая M4 write-capability требует отдельного READY threat model, OS boundary, security negative tests, backup/recovery и независимого review.
7. **Поставить телеметрию за privacy gate.** Хранить correlation IDs, timestamps, агрегированные latency/cost/outcome и redacted status. Полный prompt, ответ, rationale, retrieved memory, вложения и tool args не записывать по умолчанию. Трейс не является audit authority; источник audit state — локальные append-only события с явно объявленной моделью защиты от владельца той же Windows-учётной записи.
8. **Не выбирать sandbox без пилота.** Windows Sandbox включает сеть, clipboard и vGPU по умолчанию; mapped-folder write остаётся на host после закрытия. Для одноразового анализа недоверенного файла отключать сеть/clipboard/vGPU и монтировать только узкую read-only папку. AppContainer требует точной capability/ACL-конфигурации; Job Objects управляют жизненным циклом/ресурсами, но не образуют sandbox. [Microsoft: Windows Sandbox configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file), [AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation), [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).
9. **Оставить варианты M4 как проверяемые кандидаты, не решения.** Для CLI сравнить Quicksand и Docker Sandboxes на искусственном репозитории, без секретов/host MCP/SSH agent, с default-deny egress и проверкой guest-to-host channels, process-tree stop и restore. Docker Sandboxes в проверенных Windows docs — proprietary и ограничены поддерживаемыми CLI; Quicksand — ранний open-source. Для GUI-only провайдеров сравнить отдельную Windows VM; Windows Sandbox подходит только на одноразовую задачу и не предоставляет доменный egress allowlist. OpenShell на проверенной Windows branch не является production boundary.
10. **Проверять runtime на каждый точный профиль.** До назначения фиксировать продукт UI, runtime/версию, аккаунт, заявленную и подтверждённую модель, thread/project/custom instructions/knowledge/tools/memory/retention, cancel/resume/restart semantics. Успех старого CLI или интерфейса не подтверждает текущую ревизию. В issue Codex App Server #42622 описан version-scoped риск восстановления pending approval после рестарта; это пользовательский issue report, не независимое воспроизведение и не утверждение о текущем выпуске. [Issue #42622](https://github.com/openai/codex/issues/42622).

### Внутренние профильные рецензии и пределы

Получены три внутренние read-only Codex specialist critique по workflow/persistence, памяти/observability и Windows sandbox/security. Их общий вывод: начальная версия должна быть существенно проще будущего роя; ledger/task state отдельно от KB и telemetry; внешние эффекты требуют idempotency/reconciliation; автоматический запуск и publish не включать до измеренного M0/M4 допуска. Это одновендорная внутренняя критика, не внешний эксперт, не независимое cross-vendor review и не GitHub-native review.

Рекомендации выше — самостоятельный архитектурный синтез после чтения выбранных источников; строгая юридическая clean-room процедура не проводилась, заимствование защищённого выражения и юридическая чистота не проверялись. Полные репозитории, лицензии всех транзитивных зависимостей, безопасность исходного кода, релизы после snapshot, provider runtime и Windows isolation на реальной машине не проходили полный аудит. Внешний cross-vendor review текущей редакции требуется до закрытия T-013 и реализации.

### Минимальная запись ручной проверки знаний в M1

Архитектурный критик подтвердил, что разница FOUND/NO_MATCH/UNAVAILABLE/NOT_QUERIED уже предусмотрена, но ручной board-only процесс должен оставлять сопоставимое evidence. ## R3 follow-up: долговечность локальной доски и резервное копирование — 2026-11-17

**Область:** локальная однопользовательская доска M1, durable task/event state, crash/restart recovery и резервирование. Проверены официальные первичные документы SQLite и Microsoft; код, тесты и runtime не запускались.

### Проверенные факты

- В режиме WAL SQLite допускает одновременных читателей и писателя, но только одного писателя в момент времени. WAL требует, чтобы процессы работали на одном компьютере, и не поддерживается на сетевой файловой системе. synchronous=FULL синхронизирует WAL при каждом commit; NORMAL в WAL-режиме пропускает эту синхронизацию на каждом commit. Это влияет на сохранность последних подтверждённых транзакций при потере питания; фактическую конфигурацию нужно закреплять и проверять на целевой среде. [SQLite: Write-Ahead Logging](https://www.sqlite.org/wal.html)
- SQLite Online Backup API создаёт согласованный снимок работающей БД; источник читается короткими участками, поэтому операция не требует длительной блокировки на всё время копирования. Простое внешнее копирование файла работающей БД не эквивалентно такому снимку и может дать повреждённую копию при аварии ОС или питания. [SQLite: Online Backup API](https://www.sqlite.org/backup.html), [SQLite: Backup interface](https://www.sqlite.org/c3ref/backup_finish.html)
- Описание atomic commit SQLite основано на предположениях о поведении ОС, файловой системы и оборудования при записи и синхронизации; оно не обещает защиту от ошибок контроллера, накопителя, драйвера или произвольного повреждения файла. Режим WAL имеет собственное описание синхронизации; нельзя переносить детали rollback-journal на WAL без проверки. [SQLite: Atomic Commit](https://www.sqlite.org/atomiccommit.html)
- Windows обычно буферизует записи. FlushFileBuffers просит систему сбросить буферы конкретного файла, но Microsoft предупреждает, что частые flush после отдельных операций могут быть неэффективны. Следовательно, прикладной слой должен полагаться на корректно выбранный и измеренный режим транзакционной БД, а не добавлять ручной flush каждого события без обоснования. [Microsoft: Flushing System-Buffered I/O Data to Disk](https://learn.microsoft.com/en-us/windows/win32/fileio/flushing-system-buffered-i-o-data)

### Варианты

1. **SQLite на локальной файловой системе, один сериализованный writer.** Даёт транзакцию для связанного изменения состояния задачи и журнала событий; WAL допускает читающую панель параллельно с writer. Требует явного выбора режима durability, контроля lock/busy, checkpoint, места хранения и восстановления.
2. **Файлы JSON/Markdown как primary ledger.** Удобны для ручного просмотра и переноса, но требуют отдельного протокола атомарной записи, блокировок, индексации, дедупликации и восстановления согласованности нескольких файлов. Одна atomic replace-операция не доказывает транзакционность всего набора.
3. **Сетевой сервер БД/очередь.** Решает часть межпроцессных/межмашинных задач, но добавляет сервисную идентичность, сеть, резервирование, ACL и операционное обслуживание; для M1 преждевременен.

### Вывод и рекомендация

Оставить SQLite кандидатом для M1, не утверждая его как выбранный стек. Если он будет принят после M0: разместить живую БД на проверенной локальной файловой системе в выбранном владельцем data-root; не использовать сетевой путь; не помещать активную WAL-БД в синхронизируемую облачную папку до отдельного доказательства корректности. Для M1 требовать единственный writer, одну транзакцию для события и соответствующего состояния, подтверждение записи только после успешного commit, online backup и проверку восстановления. До READY провести целевые crash/restart, concurrent-reader, busy/lock, disk-full, backup/restore и integrity-инварианты на поддерживаемой Windows/PowerShell среде. Не объявлять долговечность доказанной без этих проверок; неизвестная надёжность оборудования остаётся residual risk.

**Профильная критика:** внутренний Codex architecture critic подтвердил, что вывод поддерживает только статус «кандидат», выделил риск облачной синхронизации живой БД и потребовал проверку целостности, внешних ключей и инвариантов журнала после восстановления. Это внутренняя консультация по переданному синтезу, не внешний cross-vendor review и не независимая проверка исходников.

**Ограничения:** использованы официальные документы, проверенные 2026-11-17. Не измерялись реальные задержки/потери на этом ПК, не проверялись filesystem/drive облачной синхронизации, локальные приложения, код SQLite binding, power-loss recovery и actual backup restore. Рекомендация не выбирает data-root, encryption, backup destination, retention, RPO/RTO или финальный storage engine; это решения M0.

### Системные требования, выведенные из отказов

1. **Повреждение не равно отсутствию.** Автоматически создавать пустое состояние разрешается только при доказанном отсутствии хранилища и его sidecar-файлов. Ошибка чтения, разбора, схемы, integrity или миграции существующего хранилища переводит приложение в read-only/fail-closed recovery; исходные данные и связанные журналы сохраняются без перезаписи до выбора владельцем процедуры восстановления. Запись поверх исходника и «восстановление» через незаметный seed запрещены.
2. **Одноразовое разрешение и локальная запись состояния — один атомарный контракт.** Для операции, полностью ограниченной локальной БД, consumption approval, ожидаемая версия/CAS, предметное изменение и append-only outcome должны быть одной транзакцией. Для внешнего эффекта сначала фиксируются approval consumption и durable intent/outbox; только после commit допускается dispatch. Сбой после внешнего эффекта, но до подтверждённой фиксации outcome, остаётся UNKNOWN и требует сверки.
3. **Ключ эффекта не равен ключу попытки.** Неизменяемая логическая внешняя операция получает operation-level idempotency key, связанный с proposal, action, target, base и payload digest. Он не меняется при перезапуске/смене `run_id`. Новый ключ означает новую логическую операцию и требует нового owner approval. Ключ используется для повторного dispatch только при проверенной provider-гарантии идемпотентности и точном совпадении payload; без такой гарантии неоднозначный исход не переотправляется.
4. **Recovery не угадывает.** `RUNNING`/`EXECUTING` после restart не превращается в QUEUED или COMPLETED только по локальному отсутствию процесса. Сначала проверяются сохранённый intent и внешний effect evidence; недостаток evidence оставляет UNKNOWN/RECONCILIATION_REQUIRED. Повтор допустим только после доказанного no-effect и новой проверки действующего разрешения.

### Обязательные future golden cases

- Существующий DB/ledger с неверным JSON, schema version, integrity check либо незавершённой миграцией: startup не перезаписывает его пустым seed, сохраняет исходник/sidecars и блокирует записи до явного recovery.
- Дублирующее/конкурирующее owner approval: CAS и одноразовый nonce позволяют ровно одно исполнение; повтор не производит второй эффект.
- Crash до local transaction commit: ни mutation, ни success event не видны; crash после commit: обе части видны вместе.
- Crash после durable external intent, после dispatch и до outcome persistence: состояние UNKNOWN/RECONCILIATION_REQUIRED; автоматического requeue/повторной отправки нет; reconciliation связывает тот же operation key, proposal и target.
- Параллельный процесс при заявленной единственной блокировке: проверка доказывает межпроцессную защиту либо приложение отказывает/запускает только одну инстанцию; process-local mutex не принимается за OS/file lock.

### Синтез и решения для нашей архитектуры

1. **Один durable task ledger, а не чат как источник истины.** Codeg и Concord support expected-version/CAS guards and atomic domain change plus event. For future storage require single writer/process lock, fencing generation, idempotency, append-only history and replay only confirmed transitions. This is a backend-neutral requirement; SQLite remains a candidate, not a selected store.
2. **Разделять claim, attempt и delivery.** External queue/worker requires atomic claim with generation/lease. Manual M1 handoff has evidence levels and is never provider receipt merely from copy/paste. A late event from an old generation cannot mutate active task.
3. **Не приравнивать отмену процесса к отмене внешней операции.** Sharelane may terminate local PIDs, but that does not prove a remote request stopped. After timeout/cancel after dispatch, classify UNKNOWN and reconcile; retry only after proven no-effect or narrowly verified provider idempotency plus separate owner approval.
4. **Измерение квоты не равно ограничению расхода.** Freshness tags and UNKNOWN help routing; a stale healthy snapshot cannot be treated as current capacity. Quota, estimate and billed usage remain distinct; a hard cap requires verifiable provider enforcement. Do not use an undocumented endpoint as a base contract.
5. **Контекстный bridge нуждается в доверенном gate.** Staging and final-assembled-payload screening are useful ideas, but a worktree, glob and shell:false are not an OS sandbox; inherited host environment expands exposure. Durable authorization/effect record must exist before external dispatch; best-effort screening log is auxiliary telemetry, not proof of authorization/delivery.
6. **Сведения из UI-тестов, README и пользовательских issues ограничены уровнем источника.** AionUI team UX tests do not prove mailbox reliability; reports of hangs/repeated billing are future negative-test scenarios, not confirmed defects.

На этой основе spec/roadmap повышены до 0.15.8-draft. NFR-AOR-002 теперь требует commit связки state/revision + event до подтверждения пользователю, блок dispatch при ошибке durable store и fencing старого run. ### Вывод для решения

- **Общение агентов — durable mailbox над task ledger.** Это наше проектное решение, а не гарантия донора: сообщение сначала сохраняется как адресованная task/run/epoch запись с message ID, sender/recipient, revision, classification и digest; уведомление лишь будит получателя. Доставка — at-least-once, дедупликация — по message ID + content digest; ack разрешён только после durable intake получателем и означает получение записи, а не принятие результата. AionCore показывает mark-read после успешной обработки prompt/run, но не подтверждает отдельную транзакцию durable intake агента. Повтор/потеря уведомления не создаёт новую работу и не стирает непрочитанное. В M1 все передачи остаются owner-mediated; прямой сетевой канал агентов и прямой доступ к board отсутствуют.
- **Адаптер проверяется на точном профиле.** Protocol, adapter и runtime/OS pin-ятся вместе; обязательные тесты имеют индивидуальный исход/evidence. SKIPPED/NOT_TESTED не может выдать SUPPORTED. ACP capability/permission negotiation не является authorization. ACP v2/TCK остаются экспериментальными свидетельствами, не security certification; session history/retention не замещает долговечную доску.
- **Process containment и isolation — разные вещи.** Job Object и child termination помогают управлять ресурсами/процессным деревом; они не ограничивают filesystem/network или account credentials. Если worktree/isolation preflight отказал, процесс не запускается и direct/in-place source checkout недопустим.
- **Несколько исполнителей не должны разделять write workspace.** AionCore shared team folder полезен для совместного обсуждения, но для нашего Git workflow нужны отдельные task worktrees/branches, conflict reservations и owner-gated integration. CAS/transaction examples из CarryCtx/AionCore — идеи для acceptance tests, не доказательство нашей будущей реализации.

1. **Повторы внешних действий требуют provider-scoped idempotency и reconciliation.** Inngest описывает ограниченное по времени окно event idempotency и предупреждает, что внешний side effect может завершиться до сохранения результата шага; восстановление/повтор тогда способен повторить действие. Источники: [Inngest idempotency](https://www.inngest.com/docs/durable-execution/guides-and-advanced/idempotency), [Inngest durable execution best practices](https://www.inngest.com/docs/durable-execution/best-practices), [Temporal Activity Definition](https://docs.temporal.io/activity-definition).
2. **Отмена не отзывает уже выданные или исполненные внешние эффекты.** Документация Inngest описывает отмену между шагами и необходимость учитывать уже завершённые side effects. Это согласуется с отдельным state invariant в спецификации: изменение task state, disable assignment generation и отзыв незанятых permits выполняются атомарно; для prepared ручной передачи нужен доказанный no-dispatch, иначе остаётся UNKNOWN/reconciliation и retry запрещён. Уже экспортированный/copied пакет и удалённый effect не отменяются локальным revoke.
3. **Разделять reasoning и детерминированное enforcement.** NIST Agent Identity design tenets и OWASP Agentic Top 10 поддерживают применение явных identity/policy/control boundaries и проверки полномочий вне свободного вывода агента. Для проекта это обосновывает owner authorization отдельно от координаторского исполнения и тестируемые guards состояния; это не является сертификацией предложенной архитектуры. Источники: [NIST design tenets](https://www.nist.gov/blogs/cybersecurity-insights/design-tenets-agent-identity-management-systems), [OWASP Top 10 for Agentic Applications](https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai/).
4. **Windows sandbox требует явного закрытия каналов и узкого mount scope.** Документация Windows Sandbox указывает, что networking и clipboard redirection включены по умолчанию; mapped folders могут предоставлять гостю доступ к host files. Если M4 будет использовать Windows Sandbox, будущая READY capability должна явно отключать ненужные network/clipboard channels и разрешать только минимальный read-only input и отдельный disposable write output, с отрицательными host-boundary tests. Пока ни sandbox, ни adapter не выбраны/не реализованы. Источник: [Windows Sandbox configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file).
5. **Уточнён Windows reserved-name deny-list.** Microsoft RtlIsDosDeviceName_U перечисляет CONIN$ и CONOUT$; общеупотребительная naming page фиксирует классические и superscript COM/LPT формы. CLOCK$ сохранён только как консервативный legacy deny-list проекта, а не как заявление о текущем документированном нормативном списке. Источники: [RtlIsDosDeviceName_U](https://learn.microsoft.com/en-us/windows/win32/devnotes/rtlisdosdevicename_u), [Windows file naming](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).
6. **Принятые review dispositions для прежнего snapshot.** DeepSeek и Antigravity подтвердили одинаковые семь файлов и digest 5fea239…; оба дали CHANGES REQUIRED. В текущую редакцию внесены: общий stop-state revoke assignment generation и неиспользованных EgressPermit, безопасное ABANDONED только при доказанном no-dispatch, иначе DELIVERY_UNKNOWN/reconciliation; дополнительная привязка account memory к digest; CONIN$/CONOUT$ и консервативный CLOCK$ deny cases; устранение повторяющихся полей permit binding; M5 review по owner-approved M0 review_policy с cross-vendor только при выбранном режиме и верификации provider identity. Antigravity не сообщил дополнительных findings по заявленным ранее lifecycle, permit, Windows, Unicode и status областям; это не опровергает findings DeepSeek и не заменяет regression/runtime verification.
7. **Повторное review и gate остаются обязательными.** Ни один отзыв на snapshot 5fea239… не является approval новых файлов. Новый content manifest будет независимо пересчитан по семи текущим путям после финального gate; затем reviewers получают digest и raw file hashes отдельно от включённого bundle. Hosted CI на новой редакции не запускался. Отдельные ранее найденные ограничения, включая attribution commits в ветке, сохраняются; R6 не является разрешением commit/push.

## R7 — Unicode security-display policy evidence — 2026-11-17

**Уровень:** R1, узкая проверка первичного стандарта; это не donor-code review и не runtime validation.

- Unicode 18.0.0 Core Specification §5.3/§5.21 отсылает к свойству Default_Ignorable_Code_Point в UCD и предупреждает не удалять такие code points вслепую; misplaced variation selectors требуют отдельной видимой обработки.
- UAX #44 18.0.0 §2.1.2 указывает, что derived property следует брать из официального data file, не пересобирать вручную; конкретный versioned listing в UCD нормативен для этой версии. В DerivedCoreProperties.txt 18.0.0 явно присутствуют U+00AD SOFT HYPHEN и U+034F COMBINING GRAPHEME JOINER в Default_Ignorable_Code_Point; файл содержит 4 174 таких code points, включая зарезервированные диапазоны.
- PropList.txt 18.0.0 содержит отдельное свойство Bidi_Control для 12 code points. Union этих двух официальных свойств надёжнее локального списка примеров. Нельзя заменять его общим правилом «все Cf»: Unicode отдельно отмечает формат-контроли, которые не default-ignorable и должны иметь видимое отображение.
- Рекомендация для будущего preview/import/egress: версионировать policy и таблицы по UCD 18.0.0; в security-sensitive строках отображать union Default_Ignorable_Code_Point/Bidi_Control как явные codepoint escapes; для произвольного текста давать escaped review view и отдельный обычный rendering с предупреждением. Сохранять raw bytes и raw SHA-256, связывать approval с версией policy и digest отображённого projection. Не удалять и не нормализовать исходные символы; наличие символов не является само по себе доказательством атаки.
- Зависимость: версия Unicode UCD изменится — это новая reviewed policy revision с golden/adversarial fixtures, а не молчаливое обновление таблицы. При неизвестной версии или несовпадении projection digest approval не выдаётся.
- Ограничение: правила описывают целевое поведение DRAFT-системы; генератор таблицы, UI, импортёр и тесты продукта не реализованы.
