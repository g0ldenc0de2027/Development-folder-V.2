### 13.1. Идеи, которые сошлись между несколькими решениями

1. **Единое состояние работы, отдельная долговременная память.** В V2 уже разделены knowledge records и operational tasks; расширять их в одну «базу всего» не нужно. Канон правил/уроки/решения и история задачи должны ссылаться друг на друга по ID, но иметь разные жизненные циклы.
2. **Одно авторитетное состояние coordinator.** При первом однохостовом этапе кандидат — локальная транзакционная БД (SQLite возможна после spike), журнал переходов и артефакты-файлы с хэшами. UI показывает проекцию, а не самостоятельно выводит статусы из чатов. Не открывать общий SQLite/WAL-файл на сетевой папке/облачной синхронизации; для реальной параллельной работы нескольких ПК нужен authenticated API и серверная БД.
3. **Сообщение, доставка, ACK и выполненная задача — разные события.** Фиксировать submitted/delivered/acknowledged/processing/result_received/verified отдельно. Если внешний CLI/GUI не возвращает подтверждение, результат — unknown, пока coordinator не сверит состояние; нельзя слепо повторять потенциально необратимый эффект.
4. **Task envelope и атомарное назначение.** Стабильные project/task/run IDs, цель, scope read/write, acceptance, контекст/классификация данных, provider, сроки/лимит, точная база/ревизия, артефакты и reviewer. Claim — атомарная операция; lease содержит поколение/fencing token, а просроченный агент не может закрыть задачу или перезаписать новое назначение.
5. **Approval не заменяет sandbox.** Coordinator проверяет полномочие на действие, владелец подтверждает точную операцию/объём/цель/срок; OS/container отдельно ограничивает исполняющую среду. Отдельно проверять prompt-injection, обходы tool authorization и фактическую изоляцию.
6. **Память не равна архиву чатов.** Сохранять итог с пользой для будущей работы, scope, источником, статусом, сроком freshness и связью с решением; не сохранять сырые беседы, chain-of-thought, секреты и временное состояние в курируемый канон. В V2 текущие записи draft, автоматического admission и обновления общей БЗ нет.

### 13.2. Предлагаемая последовательность будущей реализации — не утверждена

- **Этап 0 — сейчас:** действующие task cards, worktrees, ручная выдача и приёмка; унифицировать task envelope и фиксировать evidence без имитации автоматического обмена.
- **Этап 1 — один ПК:** локальная доска и coordinator для задач, зависимостей, событий, сообщений, run/checkpoint и артефактов; восстановление после закрытия приложения; роли и журнал полномочий. Сначала ручной relay, без «автономного роя».
- **Этап 2 — provider adapters:** подключать по одному официально поддерживаемому CLI/API/app-server, отдельно фиксировать доступные операции и состояния каждого. Не скрейпить браузер, не копировать cookies и не выдавать произвольную web-сессию за доступный API.
- **Этап 3 — sandbox:** отдельный исполняющий worker с ограничением файлов/сети/секретов и ресурсными квотами; доказать негативными тестами escape/egress/permission bypass. Worktree сам по себе этого не обеспечивает.
- **Этап 4 — несколько ПК:** после доказанной необходимости — authenticated API, синхронизируемый журнал/outbox, серверная транзакционная БД, identity и конфликт/повтор protocol; не использовать file sync как распределённую базу.
- **Этап 5 — расширенный поиск:** только после устойчивого admission/provenance/ACL/retention — локальные индексы/embeddings и измеряемый retrieval. Индекс производный и восстанавливаемый, не источник истины.

Процент/ETA строить из утверждённых и версионированных критериев приёмки и принятых evidence; отдельно показывать активную работу, ожидание владельца/провайдера и блокеры. ETA — диапазон по завершённым сходным задачам, а не точная дата от модели.

### 13.3. Ролевое оспаривание выводов

Три внутренних Codex subagents провели read-only разбор в ролях архитектуры, безопасности и workflow/эксплуатации. Они сошлись на разделении knowledge/оперативного состояния, durable state с ограниченными retry, отдельной границе authorization/sandbox и отложенном multi-PC API. Это внутреннее ролевое обсуждение одной AI-системы, не независимое ревью другой модели/производителя. Дополнительно замечен исторический UI-пример Flowise Agentflow, но его репозитории были помечены архивированными на наблюдавшейся ревизии; в shortlist зависимостей он не включён.

- Проверена локальная БЗ V2 до записи: четыре catalog-записи, включая draft ADR local-first и swarm-boundaries; правила, scope T-004, задачу T-009 и ограничения текущего KB CLI.

- Просмотрены GitHub docs/README, не полный исходный код. Не проверялись issues/PR, release assets, зависимости, advisory feeds и package/license metadata всех репозиториев; поиск не даёт измеримого полного окна результатов. Код, workflows, тесты и чужие инструменты не запускались и не копировались.
- Дополнительные источники, увиденные в discovery, не равноценно оценены и не ранжированы. Полный рынок/все аналоги не найдены и не заявляются.

**Ограничение исследования SDR-T009-GCI-01:** API-пагинация/total/incomplete_results и полный много-поверхностный аудит GitHub не собраны; это ограничивает вывод о насыщении поиска и зрелости доноров, но не отменяет найденные документированные архитектурные паттерны. До выбора технологии нужен отдельный targeted pass по GitHub identity, лицензиям, текущей поддержке, issues/releases/security и code/test locators для короткого списка.
