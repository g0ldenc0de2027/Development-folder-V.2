# Урок: контролировать Git config после синтетических fixtures

**Статус:** причина пробела в контроле установлена; происхождение старой записи config не подтверждено, 2026-11-19

## Наблюдение

Во время push-preflight локальный commit получил синтетическую identity `Scope Fixture`. Push был остановлен, удалённая task-ветка не изменилась. Общий Git config bare-репозитория содержал эту identity; установить, какой именно предыдущий процесс её записал, по имеющимся снимкам нельзя.

## Причина, подтверждённая проверками

Защитная сверка Git-fixtures сравнивала HEAD, status, refs и index исходного репозитория, но не хэшировала `config` и `config.worktree`. Git config не отражается в обычном `git status`, поэтому тестовая identity могла оставаться незамеченной. Обёртка fixture-команд также очищала только перечисленные заранее Git-переменные.

## Закрепление

Task-scope suite теперь фиксирует SHA-256 общего и worktree Git config до/после fixtures и отклоняет любое изменение. Временные Git-команды очищают все унаследованные переменные `GIT_*`, включая динамические `GIT_CONFIG_KEY_n` / `GIT_CONFIG_VALUE_n`, затем восстанавливают исходное окружение. Quality gate очищает такое окружение при проверке границ TempRoot. Локальная identity восстановлена штатным `configure-local.ps1`; перед исправлением неопубликованного commit сохранён backup ref.

## Evidence и границы

После изменения task-scope suite и полный quality gate должны пройти без изменения source Git config; проверка фиксирует именно байты config-файлов, не выводя их содержимое. Это предотвращает незамеченное загрязнение при выполнении этих suites, но не доказывает, какой процесс создал старую fixture identity, не блокирует ручное изменение config вне проверок и не заменяет отдельную проверку author/committer перед push (задача F14 остаётся открытой до её собственного acceptance). Исторические отзывы и CI на старых SHA не подтверждают новый кандидат.
