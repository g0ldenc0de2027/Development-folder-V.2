### 13.7. Синтез для нашей связки локальной и общей БЗ

| Наша потребность | Полезная комбинация идей | Проектное решение для обсуждения |
|---|---|---|
| Второй мозг без путаницы | OKF scopes/bundles + CAO Markdown content и SQLite metadata + V2 draft/verified/review | Курируемые факты и решения остаются в версионируемой БЗ; run/chat/inbox хранятся отдельно. Поиск, BM25/embeddings и граф — восстанавливаемые проекции, не источник истины. |
| БЗ в любой папке/на любом диске | OKF symlink-aware path check + CAO project identity | Корень задаётся конфигурацией/env и обнаруживается без жёсткого drive path. Records используют относительные ссылки; canonical path, project snapshot и offline copy не подменяют друг друга молча. SMB/cloud sync не считается multi-writer DB. |
| Агентам знать, кто чем занят | A2A Message/Task contract + Beads dependency graph + durable task/run journal | Стабильные task/context IDs, явные зависимости, владелец задачи, event history, отдельные delivered/acknowledged/result-verified статусы. | Доставка и авторизация остаются ответственностью собственного coordinator; протокол и issue graph сами по себе не обеспечивают изоляцию файлов/ОС.
| Координатор и интерфейс | CAO control panel + PurpleFlow lifecycle + Lightflow operator checkpoint | Локальный coordinator сначала; одна state machine, append-only event trail и атомарные snapshots; UI — проекция состояния и следующего участника. Pause/wait/blocked/retry/unknown/cancel/done различаются. |
| Несколько ИИ | CAO и Agent Workflow Kit как примеры runtime/provider differences | Подключать по одному официальному CLI/API/app-server adapter, с capability manifest, auth isolation и conformance tests. Ручная передача остаётся штатным fallback. Общая память/история чатов не обещается без API, который её предоставляет. |
| Security и фактическая изоляция | Исследованные границы in-process workflow и reservation | Human approval, command allowlist и worktree не заменяют sandbox. Worker получает минимальный доступ к файлам, сети и секретам; injection, egress, retry, unknown outcome, restore и lease fencing входят в acceptance tests. |
| Прогресс и ETA | Event-backed run states + версии acceptance criteria | Процент идёт от утверждённых критериев и принятого evidence, не от heartbeat или количества сообщений. ETA — диапазон по похожим задачам с явными ожиданиями и блокерами. |
| Несколько ПК | Разделить локальное хранилище и межузловой control plane | Первый этап — локальный coordinator и ручной relay. МежПК переходить только позже через authenticated API/server DB, identity, outbox/dedup и conflict recovery; общий SQLite/WAL через SMB/sync не использовать. |

**Кандидатные роли, без выбора зависимости:** agent-lore — отдельный слой полевых заметок ниже проверенной БЗ; agent-loom — шаблоны логических claims/leases/обязательств; A2A — внешний контракт сообщения/задачи; Beads — граф зависимостей и готовности; PurpleFlow/Lightflow — ручные workflow/checkpoints; LangGraph/Temporal — durable execution patterns. MCP Agent Mail Rust исключён по IP-ограничению. Ни один кандидат не закрывает весь контур и не становится обязательной зависимостью.

**Следующий шаг:** отдельный spec slice для local coordinator + board + task/run/message state model, затем ограниченный переносимый prototype одного официального provider adapter и crash/retry/restore/security negative tests. Спецификация остаётся DRAFT/NOT READY; реализация сейчас не начинается.

**Границы нового прохода:** выборочно изучены source/tests на pinned refs — это не полный аудит репозиториев. Нет runtime evidence, performance/security certification, полного issues/PR/release/dependency/license review и независимого review другого производителя. Numeric GitHub repository IDs не записаны. Search и REST ограничивались rate limit/неполной пагинацией. Результат подходит для выбора следующего исследования, не для утверждения технологии.

**Синтез для нашей архитектуры:**

1. Хранить исходные события/документы как доказательную основу отдельно от извлечённых фактов и курируемого канона. Для временных фактов полезны как минимум `recorded_at`, `valid_at`, `invalid_at`, `source_id`, `scope` и состояние проверки; correction должна явно supersede/retract запись, а не молча переписывать историю.
2. Фиксировать асинхронный ingestion и его outcome в журнале coordinator: queued, processed, rejected, reviewed. Ни `event_id`, ни успешный embedding не означают, что содержание стало истинным или доступным всем агентам.
3. Проверять ACL в поиске на авторитетном слое до формирования выдачи и prompt; заново проверять каждый производный индекс, экспорт и переносимый пакет. Scope агента, проекта, пользователя и сессии — отдельные измерения, не строка для красоты.
4. Считать граф, полнотекстовый индекс и embeddings восстанавливаемыми представлениями. Канонический объект хранит происхождение и lifecycle; удаление/исправление должно иметь согласованную семантику для записей и индексов, с учётом retention и приватности.
5. В файловом импорте проверять containment на каждом sink. Проверка только при загрузке недостаточна, если позже фоновой процесс заново разрешает сохранённый путь.

**Что не утверждается:** Graphiti, Mem0, Open WebUI и AnythingLLM не выбраны как основа/зависимости; лицензии, полные модели безопасности, все API-маршруты, зависимости и эксплуатация не оценивались. Исходный код не переносился. Спецификация V2 остаётся DRAFT/NOT READY; этот материал не разрешает реализацию.

**Что собираем в собственную архитектуру (чистая реализация, не копирование кода):**

1. **Развести данные по доверию и сроку жизни.** Сырой рабочий эпизод — приватный и ограниченного срока; извлечённое утверждение — кандидат с источником и датой; проверенное проектное решение — отдельная курируемая запись; оперативные статусы задач/run и личная scratch-память агента не являются каноном общей БЗ. У каждого слоя свои права, срок хранения, экспорт и удаление.
2. **Один авторитетный operational store; доска — его представление.** Список «кто чем занят», блокеры, последние события и ETA показывают события и состояния coordinator, а не независимо редактируемые копии одной карточки. Общая/проектная БЗ хранит долговременные решения и уроки; она не заменяет очередь задач и не хранит live-lock.
3. **Загружать агенту ограниченный context pack.** Формировать его из версии правил, проекта, конкретной задачи и разрешённых источников; сохранять ID/версию каждого включённого материала и причину включения. ACL проверяется на серверной/хранилищной границе до поиска и до сборки prompt, а не только при показе UI. namespace, фильтр project_id или скрытая вкладка не являются контролем доступа.
4. **Адаптеры вести к одному контракту, не к отдельным базам.** CLI, UI, MCP и будущие provider-specific интеграции используют один источник правды и capability manifest. Для каждой поверхности явно фиксировать: может ли она принять задание, подтвердить получение, сообщить прогресс, вернуть артефакт, продолжить после reconnect и какие данные отправляет наружу. Если ответ недоступен, статус остаётся unknown/awaiting_confirmation; нельзя выдавать отсутствие ответа за отказ или успех.
5. **Надёжная доставка — отдельная спецификация.** Закладывать устойчивый ID события/сообщения, идемпотентность, durable inbox/outbox, ACK, ограниченные retry/backoff, дедупликацию, offline spool и видимую dead-letter очередь. Отдельно определять срок дедупликации, восстановление после падения и ручное повторное принятие. Это требования к нашему контракту; поведение донора подтверждено только его README.
6. **Локальность проверять по возможностям.** В UI/manifest показывать раздельные egress-пути: хранение, модель, embeddings, суммаризация, relay, private-repo import, синхронизация, обновления и telemetry. По умолчанию запрещать передачу; перед включением показывать, какие категории данных и куда уйдут. Local-first, локальный пакет и MCP не заменяют фактический сетевой аудит.
7. **Переносимость не должна переносить секреты.** Общая БЗ может располагаться на любом выбранном диске; путь задаётся конфигурацией, а не вшитой буквой диска. Пакет переносимых данных обязан исключать токены, API secrets, connection strings и session files; ОС-хранилище секретов, ACL и права на съёмном носителе проверяются отдельно. Для второго ПК потребуется формально спроектировать sync, конфликты, подтверждение доставки, отзыв доступа и восстановление; копия папки не равна синхронизации.
8. **Удаление и безопасность памяти — функциональные требования.** Поддержать исправление/отзыв знания и каскадное удаление из исходного объекта, извлечённых фактов, поисковых/графовых/embedding индексов, cache/context packs, экспорта и контролируемых backup-retention. Внешняя копия, которую нельзя удалить, должна быть показана как residual risk до отправки. Извлечённые и найденные записи, сообщения и summaries — недоверенные данные, не новые системные команды; релевантность не повышает уровень доверия, prompt injection проверяется отдельными регрессиями.
9. **Асинхронная обработка должна быть наблюдаемой.** Для import/indexing фиксировать queued → processing → ready либо rejected/failed, источник, версию парсера и причину ошибки. accepted, наличие файла, индексный hit или успешный embedding не означает «проверенное знание» и не должно автоматически открывать доступ всем агентам.

**Рекомендация по этапам, а не выбор продукта:** сохранить текущий локальный файловый KB как portable канон; следующим отдельным ТЗ проектировать компактный локальный coordinator и единый event/task state с ручным подтверждением передачи между поверхностями; затем — 1–2 read-only adapters; лишь после этого — изолированные write-capable workers, approval, sandbox и egress controls; многокомпьютерную синхронизацию проектировать после определения identity, конфликтов и модели доступа. Не подключать выбранные проекты и не расширять схему KB до отдельного READY-ТЗ.

**Ограничения данного раунда:** refs сверены на GitHub HEAD 2026-11-16. Из исходников здесь выборочно проверен только участок записи OptMem; остальные новые сведения — claims авторов в README. Не выполнены независимые upstream source/security audits, review issue/PR/release history всех пяти систем, проверка лицензий, Windows install/restore tests, измерение фактического egress, нагрузочное тестирование и проверка синхронизации. Три внутренних ролевых critique (локальная память, оркестрация, privacy/security) — Codex subagents одного производителя; они не являются независимым review DeepSeek/Antigravity и не доказывают корректность реализации доноров. **Ограничение формата БЗ:** scripts/kb.ps1 ограничивает sources максимум 30 строками на запись. Пять новых доноров помещаются в каталог вместо пяти менее приоритетных прежних source IDs (AutoGen, Prefect, Agent Workflow Kit, Cognee, Khoj); их прямые ссылки и pinned refs остаются в исследовательском тексте. Расширение модели происхождения требует отдельного изменения схемы и тестов, здесь оно не выполняется.

**Синтез для нашего проекта — предложение, не принятое решение:**

1. Оставить три независимо управляемых слоя: (а) курируемая проектная/общая БЗ с происхождением и admission; (б) операционный журнал задач, сообщений, claims, ACK и запусков; (в) локальный индекс/кэш для быстрого поиска. Потеря индекса восстанавливается из канонических материалов; запись в mailbox/event log не становится знанием автоматически.
2. На первом автономном этапе оставить один активный host и root БЗ, задаваемый пользователем. Папку можно переносить между дисками/ПК после закрытия writer и проверки snapshot/integrity; это не одновременная многопользовательская синхронизация.
3. Для локального контура агентов исследовать транзакционный outbox/inbox: стабильный event ID, task/run ID, sender/recipient, schema version, scope, payload hash, created-at как справочное время, delivery status и явный ACK. Повторная доставка должна быть безопасной через idempotency key; статусы queued, claimed, delivered, acknowledged, retry, rejected, dead-letter, unknown не сводить к одному «готово». Отправитель не удаляет единственную копию до проверяемого ACK конкретного ID.
4. Claim задачи должен быть атомарным в coordinator storage и иметь истечение/renewal и fencing token. Durable outbox не решает ownership, а message ID не удостоверяет личность агента. При конкуренции нужны тесты crash/restart, duplicate/replay, lost ACK, смены владельца, просроченного lease и неизвестного результата.
5. Отдельно показать на UI фактическую доставку, последний подтверждённый sync, очередь/отказ, причину и время ошибки. Успешный HTTP response, heartbeat, push attempt или отсутствие ошибки в интерфейсе не доказывают, что событие принято обработчиком.
6. Если позже появится требование активной работы нескольких ПК, исследовать server/client sync отдельно: user/device identity, права на каждый набор данных, partial sync, авторитетность write path, tombstones, conflict inbox, revoke/rejoin, snapshots/replay, backup и egress. Для совместного редактирования текстов отдельно сравнить CRDT; не использовать его для выдачи права владения задачей.
7. Для первой версии local KB ни один из этих движков не заменяет уже выбранную файловую переносимую модель. PowerSync/RxDB/PouchDB — кандидаты только для будущего клиентского/сетевого продукта после требований и совместимого пилота; Zero — online dashboard near-miss; durable-sync — паттерн для журнала/доставки, не самостоятельная основа роя.

**Принятые уроки из ошибок источника:** не считать 200 OK подтверждением записи; ack должен перечислять подтверждённые события; timestamp с клиентского устройства нельзя считать авторитетным порядком; потерянный cursor после reset требует смены epoch или полного replay; snapshot без version-check опасен; sync при изменении session/identity должен fail-closed. Это идеи для будущих acceptance criteria, а не утверждённые требования.
