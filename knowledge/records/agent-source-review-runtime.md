### 19.2. Синтез для проектной гипотезы

1. **Три канонических журнала:** task/assignment state; message inbox/outbox; immutable event/evidence log. Они связаны стабильными IDs, но не смешиваются с долговременной БЗ. Уведомление будит агентский процесс, а authoritative state читается из coordinator.
2. **Транзакционный handoff:** при claim атомарно сохраняются владелец, generation/fencing token, lease deadline, audit event и outbox notification. Сама доставка может быть at-least-once; handler обязан быть idempotent по event ID. ACK действителен только для текущей generation и владельца.
3. **Восстановление — часть модели:** неизвестный исход команды/запуска сохраняется как `unknown`; replay не стирает старый журнал и не выдаёт прежнему worker право записи. Нужны тесты lost ACK, restart, повторного сообщения, lease expiry, смены владельца, stale completion, rollback и backup/restore.
4. **Проекты и работа с файлами:** task ID получает выделенный worktree; перед каждой записью контролируются объявленная зона, canonical repository root и target path. Для недоверенного кода отдельно применяются OS/VM/container sandbox, ограниченные credentials и сетевой policy.
5. **Регистрация проекта — preview-first:** показать создаваемые hook/config/docs, diff и возможный Git effect. Создание файлов и commit — отдельные управляемые действия; default ничего не публикует и не коммитит.
6. **UI показывает доказуемые статусы:** claimed by/lease until; last successful receive/ACK; retries; terminal error; review/evidence; owner approval. «Подключён», heartbeat или ответ агента сами по себе не означают выполненную задачу.
7. **Безопасность adapter-а — fail-closed:** нормализованная команда/аргументы, выбранный профиль и уровень прав видимы до запуска; неизвестные CLI flags, пустая policy или несовместимый runtime блокируют execution. Не использовать универсальный авто-approve.

Это синтез предложений, а не решение владельца и не изменение статуса ТЗ. На первом рабочем этапе реалистичен один локальный coordinator и переносимая файловая БЗ; multi-PC sync/server остаётся отдельным этапом после identity, ACL, conflict/revoke и backup требований.

### 20.1. Применимый вывод

1. Run/task state, долговременная БЗ, агентские заметки, сообщения и доказательства результата должны иметь разные типы/владельцев; UI строится как проекция проверяемого состояния.

3. Reviewer identity и независимость следует хранить явно: provider, runtime/CLI, model, revision reviewed, input evidence и результат. Тот же reviewer на втором проходе — дополнительная проверка, не независимая экспертиза.
4. Human gates задаются политикой по типу действия; autopilot не получает неявное право коммитить, публиковать, менять канонические правила или отправлять данные наружу.

### 21.1. Сводная рекомендация

Наиболее полезный самостоятельный продуктовый контур из найденного — локальная координационная панель с явными task claims, inbox/outbox и коротким arrival brief, но с авторитетным состоянием в coordinator store и раздельной долговременной БЗ. Память агенту передаётся минимальными пакетами с provenance. Каждый факт хранит источник и временной статус; каждое задание — owner, lease generation, evidence и точный reviewed SHA. Просроченная generation не должна завершать/изменять задачу. Это набор требований-кандидатов, а не выбор agent-coord, Letta, Graphiti или другого SDK.

### 21.2. Границы

- Два внутренних Codex subagents провели отдельные read-only source/test passes по кандидатам; это peer critique одного производителя, не внешнее межпроизводительское ревью.
- Просмотрены выбранные design/source/test-фрагменты на pins; upstream code/tests/builds не запускались. Не проводились полный security/dependency/license audit, конкурентный runtime reproducer, Windows E2E или performance test.
- **Глубина:** R2 / targeted source-and-test review. Ни один кандидат не выбран как зависимость; readiness ТЗ остаётся DRAFT/NOT READY.
