### 16.1. Синтез под наши потребности

1. **Каноническая память:** сохранять новые наблюдения в отдельной очереди предложений; до проверки агентам их нельзя выдавать как подтверждённые факты. У каждого предложения хранить scope, источник/хэш, автора/сессию, время, неопределённость и связь с конфликтами. Канон повышает только владелец; исправление — supersede/retract с историей. Проверить секреты/PII и допустимость egress до записи/индексации.
2. **Поиск:** в обычный рабочий context включать только утверждённые записи, подходящие конкретному проекту/задаче; предложения и отклонённое исключать. Полный корпус, личные чаты или память провайдера не синхронизировать автоматически.
3. **Локальная координация:** один локальный coordinator держит задачи, попытки выполнения, события и сообщения. Для первой версии одной машины рассмотреть локальную транзакционную БД, но подтвердить выбор нагрузочными и восстановительными тестами. Её live-файл нельзя синхронизировать как общую БД между ПК.
4. **Надёжность задания:** stable IDs, dependency graph, атомарный claim, lease expiry, монотонный fencing generation, idempotency key, bounded retries/backoff, append-only lifecycle events. Просроченный исполнитель не может завершить работу поверх новой попытки. Lease координирует, но сам не ограничивает доступ к файлам/ОС.
5. **Сообщения и handoff:** отдельно моделировать отправлено, доставлено/получено (ACK), выполняется, результат сдан, проверено, ошибка/блокер/отмена. Доставка может быть at-least-once; дедупликация обязательна. Нельзя переименовывать ACK в «задача выполнена».
6. **Безопасность:** MCP и протокол — интерфейсы, не авторизация. Проверка личности/ролей, task/file scope и действий должна происходить на сервисе/OS gate; UI и Markdown доска показывают состояние, но не являются источником истины. Никакой agent self-promotion, обход review или выдача секретов.
7. **Этапы:** сначала один компьютер, переносимый пользовательский `data-root`, одна активная задача/worker и ручной владелец-диспетчер; далее несколько локальных adapters и независимый review; потом ограниченная параллельность и очередь; только затем multi-PC API/server DB, аутентификация, offline sync/conflict resolution и внешние wake callbacks.
8. **Не делать вывод о доступности аккаунта:** наличие MCP/A2A/bridge проекта не подтверждает, что Codex/ChatGPT/DeepSeek/Antigravity разрешают unattended API, историю чужих сессий или внешние callbacks. Каждый provider adapter требует отдельной проверки официальной поверхности, scopes/consent, egress и ограничений тарифа.

### 17.1. Что это меняет в нашей архитектурной гипотезе

Новые источники усиливают составную, а не «один донор — один продукт» схему:

1. **Шесть разных слоёв и проекций:** утверждённые долговечные знания; очередь недоверенных предложений; оперативный реестр задач и сообщений; приватное состояние сессии/запуска; перестраиваемые поисковые индексы и read-only dashboard. Статусы одной сущности не дублируются в конкурирующих файлах.
2. **Task ledger отдельно от mailbox:** у сообщения — immutable ID, адресат, conversation/task correlation, idempotency key, `sent/delivered/acked`; у задачи — собственные `proposed/approved/claimed/running/blocked/review/accepted/closed`, версия состояния, lease/fencing и доказательство результата. Получение сообщения не означает принятие задачи, а ACK не означает выполнение.
3. **Полномочия через coordinator/executor:** агентская identity устанавливается доверенной локальной регистрацией; human grant ограничен проектом, агентом, категорией/действием и сроком. Проверку полномочия повторять непосредственно перед реальным эффектом; self-reported capability — только сигнал доступности. Координационный lease и MCP не являются sandbox: для запуска CLI нужны отдельные ограниченные process/OS-права. Запрет permission-bypass — базовое условие.
4. **Adapter boundary:** общий контракт `detect → start → observe/poll → cancel → normalize result`, а provider-specific parser/version остаётся в адаптере. Сохранять observed provider/model/version отдельно от запрошенных; различать `success/failure/aborted/unavailable/unknown`. Секреты и сырые трассы остаются в локальном data-root и не попадают в общий knowledge context автоматически.
5. **Прогресс и ETA:** dashboard — проекция coordinator ledger, read-only по умолчанию. Показывать отдельно завершённый checklist, принятую проверенную работу и блокеры; у каждого процента должны быть знаменатель и ссылка на evidence. ETA — диапазон/сценарий на основании фактической истории похожих задач с уровнем уверенности; при недостатке истории — `unknown`, не фиктивное число.
6. **Развёртывание по этапам:** сначала локальный coordinator и portable data-root на основном ПК, экспорт/backup/restore с проверкой, без общей SQLite/WAL по синхронизируемой папке; затем adapters, dashboard и gated dispatcher; multi-PC transport добавлять после отдельного решения о server/auth/ACL, очереди офлайн-конфликтов, отзыве и восстановлении.

Это проектные гипотезы для будущего ТЗ, не утверждённая архитектура. Ни один из четырёх источников не выбран зависимостью или базой продукта. Идеи извлечены в собственной формулировке; код, prompts, конфиги и assets не копировались.

### 18.1. Что взять в нашу проектную гипотезу

1. **Три первичных объекта, не один чат:** очередь задач/владение; сообщения и их подтверждения; immutable event/evidence log. Для реальной работы агент принимает handoff/claim отдельно от чтения сообщения; review/verification закрывают результат.
2. **Модель actor → scope → action → expiry:** идентичность задаётся доверенной системой, capability используется для поиска подходящего исполнителя, а разрешение повторно проверяется при записи/запуске. Monitor token должен быть ограничен временем, объектами и read-only endpoints. Ни MCP, ни токен чата, ни local dashboard не являются sandbox.
3. **Рабочая доска — обзор и операторский контроллер, не источник истины:** UI читает состояние из coordinator; destructive/side-effect actions показывают preview, target path/branch и требуют явной owner approval. Board-generated scaffolding/commit не должны возникать как побочный эффект импорта.
4. **Поддержка агента имеет уровень доказательства:** заявлен в README, проверен статически по контракту, smoke-tested на Windows, CI-covered на pinned CLI/version, либо production-qualified — это разные статусы. `Tier 2`, alpha и experimental workflows нельзя сводить к “поддерживается”.
5. **Шаблоны permission flags — критический security setting:** отсутствие настройки не должно означать обход подтверждений. Любой CLI adapter должен fail closed, показывать сформированную команду и применённую policy, а права ограничивать process/OS boundary.
6. **Локальная БЗ и агентский bus остаются разными доменами:** durable messages и run history полезны как оперативная память; в общую БЗ попадут только отдельные proposal после происхождения, проверки, редакторского решения и scope/ACL-проверки.
7. **Не начинать с 65 tools и multi-runtime matrix.** Сначала малая поверхность команд и одна безопасная local session; добавлять provider/runtime только после compatibility tests, permission-policy test и recovery review.

Это предложения для будущего ТЗ, не принятые требования. Из рассмотренных продуктов ни один не подходит как готовая основа без потери требований: Okto Nexus — ограничительная лицензия и plaintext session secrets; Hive — bypass defaults, alpha/Windows Tier 2 и BUSL; Kandev — AGPL и более тяжёлый multi-runtime scope; Agentic Kanban/Agent Bus — узкий/single-user либо отсутствие auth. Сходство с нашим проектом не является доказательством качества или безопасности.
