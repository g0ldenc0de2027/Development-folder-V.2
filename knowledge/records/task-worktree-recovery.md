# Урок: глобальный контроль состояния linked worktree

Дата: 2026-11-18
Статус: draft

## Наблюдение
Незакоммиченные изменения накапливались в отдельных ветках, хотя новая работа продолжалась в других worktree. Обычная проверка активной папки не показывала состояние соседних веток. Untracked и игнорируемые файлы, в том числе .vs, могли не попадать в привычный краткий статус; bare admin repository при этом не является рабочей копией и не принимает обычный git status.

## Причина
Процесс требовал начать чисто, но не запускал обязательный глобальный audit перед созданием задачи. Pre-commit и pre-push hooks проверяли отдельные свойства текущего commit/публикации, но не останавливали действие при грязном соседнем worktree. Создание worktree вручную было допустимо, однако проверка всех зарегистрированных копий и восстановление после interruption оставались процессными договорённостями. Поэтому не было раннего fail-closed сигнала, а отсутствие результата проверки можно было принять за чистое состояние.

### Вторичная причина: hook-контекст в regression harness
При реальном pre-push regression suite запускала fixture-команды git -C, наследуя GIT_DIR, GIT_WORK_TREE, GIT_INDEX_FILE, GIT_COMMON_DIR и GIT_PREFIX от hook. В результате setup тестового bare-репозитория воздействовал на настоящий локальный репозиторий: T-015 HEAD/index переключились на fixture, локальный main был заменён, и hook отказал до отправки. Backup показал, что все 66 путей последнего корректного T-015 commit 86e7f7f5bb3131f1c9fe96b04b92151a18cb85b9 на диске сохранили точные байты. После проверки резервной копии refs/HEAD/index восстановлены локально; remote не менялся. Этот случай показал, что изолировать Git-контекст должен и тестовый harness, а не только проверяемый production script.

### Повторная калибровка: 2026-11-18

Read-only-аудит T-015 выявил, что проверка только `git worktree list` не видит оставшийся физический каталог `.worktrees/T-NNN`, если Git его не зарегистрировал. Кроме того, удаление только пяти hook-переменных оставляло другие `GIT_*`, включая `GIT_CONFIG_COUNT`, способные подменить effective config или object store. Первая реализация очистки через `.NET SetEnvironmentVariable(name, $null, 'Process')` оставляла пустую переменную в Windows PowerShell; hook-context regression воспроизвёл `fatal: not a git repository: ''`. Исправление использует `Remove-Item Env:` с точным восстановлением исходного окружения.

Закреплено: аудит сравнивает физические каталоги `.worktrees/T-NNN` со списком зарегистрированных worktrees и блокирует orphan, не изменяя данные; reparse point на корне `.worktrees` блокируется; fixture и production Git subprocesses очищают все `GIT_*`. Новые тесты покрывают пустой production quarantine, missing/prunable worktree, orphan-каталог, несоответствие ID ветки и каталога, config injection и hook context. Целевой suite прошёл 17/17; это доказывает поведение synthetic fixtures на проверенной редакции, но не исключает обход локальных hooks или гонку с внешним процессом.

### Повторная калибровка после независимого ревью: 2026-11-18

На PR #11 Antigravity проверил точный head be8860cb8f4ecfa1111420ac9ffe50c344659f57 и дал APPROVE с двумя low-наблюдениями; DeepSeek сообщил APPROVE без уязвимостей для той же пары SHA. Эти отзывы относятся только к тому head, до исправлений ниже.

1. Безопасный GIT_PREFIX=config/ для вызова Git из вложенной папки отклонялся как неожиданный. Адресная проба прошла после проверки, что префикс относительный, без компонентов . или .., реально существует и остаётся внутри текущего worktree; traversal ../outside/ остаётся заблокирован.
2. Точный quarantined-файл с кириллическим именем не совпадал с git status --porcelain, когда effective core.quotepath=true возвращал C-escaped путь. Status-вызовы теперь явно используют core.quotepath=false; manifest и сравнение путей остаются точными.

Во время добавления второй регрессии был замечен отдельный дефект контроля тестов: некорректно разделённый блок пропустил исходный pre-push case, но suite завершилась с кодом 0. Оба runner теперь сравнивают число реально выполненных cases с явным ожидаемым count (25 identity, 19 worktree) до печати PASS. Путь для scratch тоже должен быть коротким: глубокий temp root вызвал Windows Filename too long / GIT_DIR too big, поэтому такой прогон считается ошибкой окружения и не свидетельствует о дефекте проверяемого кода.

На предыдущем кандидате до исправления default root suites прошли 25/25 и 19/19; это исторический результат той редакции. Полный gate и новые hosted/review evidence обязаны быть привязаны к итоговому commit; изменение head делает оба прежних AI-отзыва устаревшими. Запись остаётся draft, автоматического принятия урока нет.

Источники: владелец; Antigravity и DeepSeek, PR #11, 2026-11-18; задача T-015.

### Повторная калибровка: выбор корня audit-скрипта, 2026-11-18

При запуске task-worktree-audit.ps1 по абсолютному пути из посторонней папки без параметра RepositoryRoot скрипт брал корень из Get-Location. Воспроизводимый вызов из другого checkout завершался как not a git repository либо мог проверить не тот проект. Default изменён на родитель scripts-папки самого скрипта; явный RepositoryRoot по-прежнему позволяет fixture и вызывающей стороне указать другой worktree. Новый synthetic regression запускает копию скрипта из unrelated cwd без RepositoryRoot и требует WORKTREE-AUDIT=PASS.

В начале тестовая копия лежала в общем seed и случайно загрязняла обе fixture-worktree. Её перенесли только в main fixture и удаляют отдельным synthetic commit после проверки; quarantine fixture остаётся изолированной. Worktree suite завершилась 20/20, включая прежние pre-commit/pre-push случаи. Реальные refs и рабочие данные этим сценарием не изменяются.

Ограничение: default теперь устойчив к ошибочному shell cwd, но вызывающая сторона всё ещё может намеренно передать неверный явный RepositoryRoot; отдельная проверка правильности такой аргументации остаётся ответственностью вызывающего workflow.
## Закрепление
- scripts/task-worktree-audit.ps1 -Mode Audit проверяет все зарегистрированные worktree, физические каталоги `.worktrees/T-NNN`, tracked, staged, unstaged, untracked, missing/prunable записи, связь task ID с веткой и игнорируемые .vs. Вложенные Git-вызовы временно удаляют все process `GIT_*` и восстанавливают исходное окружение.
- pre-commit повторяет глобальный audit и допускает только staged write-set текущего worktree; pre-push требует чистое состояние и повторяет audit.
- Regression suite проверяет чистые/грязные и отсутствующие worktrees, orphan-каталоги, mismatch ID, ignored .vs, точный synthetic quarantine, пустой production quarantine, hooks и изоляцию Git environment/config в fixtures и production subprocesses.
- Создание новой задачи начинается только после успешного audit. После interruption сначала обновляется handoff и продолжается исходная задача; автоматических reset, clean, stash или удаления нет.

### Повторная калибровка: Git в Windows sandbox Codex, 2026-11-18

В T-015 sandboxed-вызовы `git status` и `git diff --check` завершились `fatal: this operation must be run in a work tree`, хотя `git rev-parse --is-inside-work-tree` сообщал `true`, `git ls-files -m` перечислял изменения и чтение файлов работало. При read-only повторе тех же команд в одобренном контексте вне sandbox статус показал тот же checkout и пять modified-файлов; `git diff --check` завершился успешно, HEAD остался `c6e939f1abd7ee9d8088b4ada66365f7915296e6`. Это подтверждает ограничение sandbox-исполнения для этой проверки, а не повреждение worktree. Похожая последовательность описана в открытом [Codex issue #52527](https://github.com/openai/codex/issues/52527), но конкретная низкоуровневая причина на этом хосте не установлена.

При таком симптоме сначала сверить `--is-inside-work-tree` и `--show-toplevel`, затем повторить только read-only `status`/`diff` в утверждённом execution context, который может войти в exact checkout. Не менять `.git/config`, не запускать repair/reset/clean и не объявлять дерево чистым на основании неудачного sandbox-вызова. Если та же ошибка остаётся вне sandbox, отдельно исследовать указатели `.git`, регистрацию worktree и разрешения файловой системы; автоматическое восстановление запрещено.

### Калибровка: fail-closed границы и восстановление Git config, 2026-11-18

Read-only review T-015 на более раннем опубликованном SHA выявил, что read-only recovery source T-013 запрещался в pre-commit, но не явно в publish audit; также standalone audit проверял reparse point у worktree, но не у всех входных корней/конфигурации и их предков. Исправление расширило проверку существующих путей и предков и добавило synthetic Publish regression для T-013. Это снижает риск ошибочной публикации, но не обещает устойчивость к файловой гонке после проверки.

Настройка identity выполняет несколько проверяемых `git config --worktree` операций. Между ними сбой может оставить частичную конфигурацию; успешное завершение обязательно включает verifier, иначе хуки и gate должны отказать. Повторный `configure-local.ps1 -IdentityOnly` повторяет целевые значения. Не добавлять автоматический rollback без механизма блокировки конкурирующих изменений: rollback snapshot может перезаписать более новые настройки. Это восстановимый частичный сбой, не атомарная транзакция.

### Повторная калибровка: точный зарегистрированный .worktrees/main, 2026-11-19

Read-only audit T-015 блокировал чистый зарегистрированный linked worktree по пути .worktrees/main: проверка имени ^T-\d{3,}$ выполнялась до сравнения канонического пути со списком git worktree list. Это ложный отказ, а не основание отключать проверку физических каталогов. Исправление вычисляет полный путь и разрешает basename main только при точном совпадении с зарегистрированным worktree. Незарегистрированный main и любые другие неожиданные каталоги остаются заблокированы; audit не удаляет их.

Synthetic regression подтверждает оба направления: зарегистрированный .worktrees/main проходит; после снятия регистрации одноимённый каталог с sentinel-файлом блокируется, файл сохраняется. На предыдущей редакции worktree suite прошёл 24/24; после добавления real-hook case текущая редакция прошла 25/25 (см. ниже). Это fixture evidence, не полный gate.

### Калибровка: реальные Git hooks и bare admin, 2026-11-19

Два уже отслеживаемых T-008 замечания P2-01/P2-02 проверены в настоящем локальном Git hook-контуре, а не только через shim audit. P2-02 воспроизводился потому, что audit subprocess очищал все GIT_* переменные, включая временный GIT_INDEX_FILE, созданный Git для commit -a и commit с pathspec. Исправление в scripts/task-worktree-audit.ps1 принимает только проверенный index текущего worktree для commit-mode status; произвольный index вне worktree по-прежнему завершается отказом.

Проверка P2-01 выявила дополнительный корневой случай: при bare admin и заранее настроенном worktree-scoped core.bare=false команда git worktree list --porcelain, запущенная из linked worktree, показывает путь common Git directory без отдельной строки bare. Инициализатор ошибочно принимал эту схему за небезопасный общий core.bare=true, поэтому configure-local.ps1 не мог автоматически восстановить identity через pre-commit. Теперь bare admin распознаётся по точному совпадению перечисленного пути с commonDir; для обычного non-bare repo commonDir остаётся .git и не совпадает с рабочим каталогом.

Новые проверки сначала воспроизвели отказ GIT_IDENTITY_SHARED_CORE_BARE_UNSAFE, затем после исправления прошли: Git identity regressions 31/31 и worktree regressions 25/25. Реальный pre-commit тест проверяет commit -a, pathspec commit, точный Git temporary index, отказ для произвольного внешнего index, обязательный отказ первой попытки после repair и успешный отдельный повтор; gh заменён локальным synthetic shim с проверкой, что именно он разрешён командой, сетевые обращения не выполнялись. git diff --check также PASS.

Кодовая часть T-015 опубликована commit `1c675cc61ba47b7280e3b05083ce66539bfbf4d2`; локальный и pre-push quality gate прошли, а hosted run `#44471405219` завершился SUCCESS на merge-result `a28d75c53172ac1bde86ed33de43ded53582d671` с точными base/head родителями. Эти доказательства относятся к code checkpoint, не к последующим изменениям карточки, handoff и AGENTS. T-015 остаётся открытой до свежего независимого review итогового live head. T-008 остаётся открытым до безопасной интеграции и обновления его карточки; P2-03 по live PR #12 и независимые P3 follow-ups остаются отдельными пунктами.

### Калибровка: уборка временных артефактов агента, 2026-11-19

Владелец показал в Корзине восемь пустых каталогов `.codex-t008-*`, удалённых утром 2026-11-19; на скриншоте размер каждого — 0 КБ. Колонка исходного расположения обрезана. Владелец подтвердил, что это оставленные Codex папки. Текущий read-only запрос Windows Shell не нашёл соответствующих записей; точную команду-создатель установить не удалось. Точный шаблон `.codex-t008-` не найден в scripts/tests V2. Проверенные quality-gate и regression runners используют собственные уникальные временные корни с cleanup в `finally`, поэтому считать их доказанным источником этих восьми каталогов нельзя. Codex не восстанавливал и не очищал Корзину. Это подтверждённый сбой уборки собственных артефактов при неизвестном точном месте создания; он не разрешает удалять произвольные ignored/untracked файлы.

При первом полном quality-gate запуске Codex выбрал слишком длинное имя внешнего temp-корня; вложенный Git fixture завершился `Filename too long`. Это ошибка параметров запуска, а не дефект проекта: после сбоя точные HEAD, ветка, refs, worktrees и исходный Git-status совпали; выделенный temp-каталог отсутствовал после cleanup. Для повторного gate нужен короткий уникальный temp-корень; перед запуском проверяется полный путь наиболее глубокой fixture.

Закрепление: AGENTS.md требует уникальную область запуска `temp/<task>/<agent>/<run-id>` либо явно проверенный внешний temp-каталог, `try/finally`, удаление только собственного точного каталога и заключительную проверку tracked/untracked/ignored остатков. Пользовательские данные, inbox, backups, recovery snapshots и чужие временные области не удаляются. Ошибка cleanup теперь считается неуспешным завершением. Точную программу, создавшую показанные каталоги, и наличие дополнительного source-level cleanup-дефекта не проверял.

### Калибровка: LF при редактировании в Windows, 2026-11-19

При исправлении handoff бинарная правка внесла CRLF в LF-only файл; дальнейшая вставка абзаца через `[Environment]::NewLine` внесла CRLF в запись знаний. Следующий полный quality-gate запуск это поймал на regression `Expected LF-only line endings` до commit/push. Причина — Windows-ориентированная запись текста без сохранения формата файла. Файл нормализован к tracked LF; каталог БЗ пересчитан. Для следующих правок использовать LF-aware patch и проверять `git ls-files --eol` на каждом изменённом текстовом файле перед gate. Существующий gate уже содержит regression, поэтому отдельный дублирующий тест не нужен.

Evidence for commit 55970f4d7db0429a2c5d9c64c7f617965d0d5815: pre-push passed with 69 local text files; hosted quality-gate #44484559621 passed on merge-result 40dccdbe36672be9c7638a745ea846396e309f2c with 65 hosted text files. These counts describe separate runs. The earlier unpublished recovery checkpoint is preserved locally and is outside this evidence.

## Ограничения
Локальные Git hooks можно отключить или обойти; это снижает риск случайного продолжения поверх грязных деревьев, но не является абсолютной защитой. Аудит — снимок состояния: конкурентное изменение worktree после проверки возможно, поэтому pre-push повторяет проверку. Сам `task-worktree-audit` не удаляет неизвестные артефакты. Regression runners удаляют только принадлежащие им уникальные fixture-каталоги; это не разрешение на очистку произвольных временных, ignored или пользовательских путей.
